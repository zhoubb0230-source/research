# 洞察服务 · 骨架与任务包

把"业务洞察"从**一次性需求**做成**可复用服务**的那一层。

## 一句话

**骨架只有一条，需求差异全部由任务包参数表达。** 新需求 = 新任务包，不是新流程。

## 为什么不是"支持 N 种洞察范式"

最初的做法是列范式清单：筛选排序、格局测绘、单标的评估、归因解释、监控追踪……
问题是每来一个新需求就要补一条——**那不是抽象，是待办列表**，而且永远补不完。

拆开对比会发现骨架完全一样，差异只有两处：**对象集合从哪来**、**聚合成什么**。
"单标的评估没有枚举阶段"是错的——它的枚举退化成了 n=1。**差异是退化，不是缺失。**

所以：

- **类型只有一个**（`spine.md` 的九动作骨架）。加类型要动架构，必须收敛。
- **预设可以有几十个**（`presets/`）。预设只是常见参数组合的快捷方式，加一份 JSON 即可。

## 现有预设

| 预设 | 决策问题 | 对象单位 | 主要维度类型 | 算子 | 证据时效 |
|---|---|---|---|---|---|
| `opportunity-screening` | 未来 3 年优先投入哪 5–8 个新业务方向 | 业务机会 | ordinal（6 维带权重） | `rank` | 24 个月 |
| `landscape-survey` | 引入哪类 AI Coding 工具、自建采购边界在哪 | 产品/工具 | categorical 为主 | `cluster` + `matrix` | 6 个月 |

这两份参数取值几乎完全不同——对象单位、维度类型、算子、证据等级实例、时效要求——但走同一条骨架。**它们是这套抽象的验证用例**，不只是样例。

## 用法

```bash
# 1. 复制一份最接近的预设
cp presets/landscape-survey.brief.json presets/my-need.brief.json

# 2. 改参数（至少要改：decisionQuestion、subject、criteria.dimensions、evidencePolicy.grades）

# 3. 校验
python3 checks/validate_brief.py presets/my-need.brief.json
```

校验器无第三方依赖即可运行（跨字段规则全部执行）；装了 `jsonschema` 会额外做字段形态校验：

```bash
pip install jsonschema   # 可选
```

自测夹具：

```bash
python3 checks/validate_brief.py checks/fixtures/broken.brief.json   # 期望 exit 1，报出十余项错误
```

## 回环：证伪发现问题之后

骨架不是线性的。质疑审查专家报出问题后，**质疑类型决定返工回到哪一步**：

| 质疑类型 | 回到 |
|---|---|
| `evidence_missing` / `evidence_weak` / `source_grade_too_low` / `stale_data` | ③ 取证 |
| `confirmation_bias` | ③ 取证 —— **补的是反向证据** |
| `scope_mismatch` | ④ 核证 → ⑤ 刻画 |
| `anchor_misapplied` | ⑤ 刻画 |
| `counterexample` / `causal_overreach` | ⑧ 仲裁（判断问题，补证解决不了） |
| `definition_drift` | ① 界定（**须人工**，唯一能改 brief 的路径） |

三条约束保证它收敛（详见 `spine.md` §4）：

1. **只回不进**：补了证据不能直接改分，必须重走 核证 → 刻画 → 聚合。否则新证据绕过核证进入评分。
2. **单调收敛**：每次返工必须产出新的 `evidence_id`，否则判该质疑成立，不再重试。
3. **全局重算**：任一对象刻画 `revision` 变更 ⇒ 聚合标记 `stale` ⇒ 全量重排；
   证伪阶段做 Top K+3 缓冲带，避免重排后新进 Top K 的对象未经证伪。

预算在 `rework` 字段里配（`perSubject` / `globalShare` / `requireNewEvidence` / `topKBuffer`）。

## 三条最容易写错的地方

1. **闸门尽量设 `evaluateAfter: enumerate`。** 闸门前置能省一个量级的取证成本；顺序错了成本差得非常明显。
2. **数据不可得一律用 `defer` 不用 `reject`。** 数据缺失是我们的信息问题，不是对象的质量问题。用 reject 会让系统系统性偏向"公开数据充分"的成熟对象——而那里机会最少。校验器会拦这个错。
3. **`maxAgeMonths` 必填，强迫你想清楚时效。** 工具能力对比 6 个月就可能过期，产业规模数据 24 个月仍可用。写错这个，报告会拿着过期证据下当期结论。

## 关于退化

任务包里发生的每一次退化（枚举退化、刻画退化……）都要记进 `degradations[]`，
并**在报告首屏显式呈现**。这与"数据缺失必须显式暴露"是同一条原则：**降级必须可见。**

后五个动作——取证、核证、证伪、仲裁、成文——**永不退化**，任何档位、任何兜底情形都必须完整执行。
任何"为了快一点"而跳过其中之一的设计都是错的。

## 关于本目录中的数字

不含任何真实产业数据或产品数据。预设里出现的数字全部是**判据阈值与配置参数**
（权重、锚点门槛、时效月数），不是对某个对象的事实断言。
真实数据只能由专家团在运行时带来源产出，经发布闸校验后入库。
