# 聚合算子集

骨架的第 ⑥ 步。把「逐对象逐维度的刻画结果」变成「可供决策的结论结构」。

**算子集刻意保持收敛**——它是数学性质的（怎么把矩阵折叠成结论），不是业务性质的。
当前五个：`rank` 排序、`matrix` 制表、`cluster` 分组、`verdict` 单结论、`trend` 随时间演变。业务差异由维度与判据表达，不由算子表达。**遇到新需求时，先确认现有算子真的表达不了，再考虑加算子。**

算子**可组合**：`aggregation` 是数组。格局类洞察常用 `matrix` + `cluster`。

置信度机制对所有算子通用，见 `spine.md` §5。

## rank · 加权排序

| 项 | 内容 |
|---|---|
| **输入要求** | ≥1 个 `ordinal` 维度，且全部 `ordinal` 维度的 `weight` 之和为 100 |
| **输出** | 排序榜单 + 终分 + 置信度分层 + 逐对象的选择理由与头号风险 |
| **典型需求** | 从大量候选中筛出值得投入的少数 |

**计分**

```
基础分 = Σ (weight × 维度得分 / 10)     NA 维度的 weight 从分母扣除后归一化
终分   = 基础分 + Σ 修正项（config.adjustments）
```

**硬规则**

- **先按置信度分层，层内按终分降序。** 不做单一维度的线性排名。
- **`low` 置信度对象不得直接进入下一步深度处理**，先补证。高分 + 低置信度最可能的解释是"缺失数据被乐观填充"。
- 榜单必须同时呈现「选择理由」与「最可能错在哪」。只列理由的榜单会被当成推荐清单。

**误用**

- ❌ 把门槛型判据（能力可迁移性、法律红线）塞进加权公式 → 应该是 `gate`，否则"做不了但分高"的对象会冒到榜首
- ❌ 给档间分（7 分、9 分）→ 必须命中锚点档位
- ❌ 用 `rank` 做格局测绘 → 给每个厂商打个总分没有信息量，用 `matrix`

## matrix · 特征矩阵

| 项 | 内容 |
|---|---|
| **输入要求** | ≥2 个维度，类型不限 |
| **输出** | 对象 × 维度矩阵 + **关键差异点**（真正拉开差距的 3–5 个维度） |
| **典型需求** | 业界现状测绘、方案横向对比 |

**硬规则**

- **必须产出「关键差异点」，不能只丢一张全量矩阵。** 罗列 30 个特征的表格没有洞察，挑出真正分化的那几维才有。
- 每个单元格要么有 `evidence_ref`，要么是 `未获取`。**不允许留空**——空白会被读者默认为"否"。
- 维度取值域外的值记 `other` 并在报告中单独列出（它往往是新路线的信号）。

**误用**

- ❌ 把矩阵当成结论 → 矩阵是材料，差异点才是结论
- ❌ 维度选择迁就"能查到什么" → 应由 `decisionQuestion` 决定维度，查不到就记 NA

## cluster · 分组

| 项 | 内容 |
|---|---|
| **输入要求** | ≥1 个 `categorical` 维度（`config.byDimension` 指定按哪维分组） |
| **输出** | 分组 + 每组的共性与代表对象 + 组间边界说明 |
| **典型需求** | 技术路线分类、玩家阵营划分 |

**硬规则**

- 分组依据必须是**已声明的 categorical 维度取值**，不是模型的主观归纳。
- 落在取值域之外的对象单独成组（`other`），**不要硬塞进最接近的组**——它可能正是新路线。
- 每组必须说明「组间边界」：什么样的对象会从这组划到那组。边界说不清说明维度取值域设计有问题。

**误用**

- ❌ 先分组再找理由 → 确认偏误的典型形态
- ❌ 组数迁就美观（"分成三类比较整齐"）→ 组数由取值域决定

## verdict · 单一结论

| 项 | 内容 |
|---|---|
| **输入要求** | 任意 |
| **输出** | 结论 + 支撑依据 + **反方论证** + 结论成立的条件 |
| **典型需求** | 单标的评估、是否决策、兜底档 |

**硬规则**

- **必须写「反方论证」与「结论在什么条件下不成立」。** 单结论最容易滑向单边叙事，这两项是强制的平衡装置。
- 对象数 = 1 时这是退化形态：聚合即结论本身。
- 兜底档（`dimensions` 为空）默认用本算子，输出是带证据链的自由格式分析。

**误用**

- ❌ 用它掩盖对象其实有多个（该用 `matrix` 或 `rank`）
- ❌ 结论比证据强 → 措辞强度必须与置信度匹配

## trend · 随时间演变

| 项 | 内容 |
|---|---|
| **输入要求** | ≥1 个 `temporal` 维度或 ≥2 个时点的基线；`config.baselines[]` 指向基线快照 |
| **输出** | 变化清单（新增 / 消失 / 取值变化 / **未变**）+ 方向判断（上升/下降/拐点）+ 每项变化的双端证据 |
| **典型需求** | 周期性追踪、演进脉络梳理、竞对动态监控 |

**`diff` 是 `trend` 在 n=2 时的退化形态，已并入本算子。**
先前把它单列成独立算子，违反了本骨架自己的"退化不是缺失"原则——两个时点的比对不是另一种折叠，
是同一种折叠的最短情形。

**硬规则**

- **"未变"也要输出。** 只报变化，读者无法区分"真没变"和"这次没查"。
- 每项变化必须给出变化前后**两端的 `evidence_ref`**。单边证据不能证明变化。
- 基线超过 `evidencePolicy.maxAgeMonths` → **不能直接比对**，须先重新核证基线。
- **跨 brief 版本的基线不可直接比对**（口径变了，差异无意义）。基线快照必须记录 `briefVersion`。
- 方向判断（上升/下降/拐点）是**判断不是事实**，必须标注，并给出判定所依据的时点数。

**误用**

- ❌ 把"我们这次没查到"报成"消失了"
- ❌ 用两个时点断言趋势 —— 两点只能说变化，说不了趋势
- ❌ 复用过期或跨版本基线

## rank_hypotheses · 解释排序

| 项 | 内容 |
|---|---|
| **输入要求** | `subject.unit` 为解释假说，`source.type = hypothesis_generation` |
| **输出** | 假说排序 + 各自的支持证据、反证、以及**未被排除的竞争解释** |
| **典型需求** | 归因分析（某指标为什么变化、某事件为什么发生） |
| **与 `rank` 的关系** | 结构上是 `rank` 的特化。**保留它作为独立算子，是因为算子名本身承载规则**——并入 `rank` 后，「保留竞争解释」「反证与正证等重」这两条会退化成容易被忽略的 config 开关 |

**硬规则**

- **必须保留竞争解释，不能只留第一名。** 归因分析最大的失败是过早收敛到一个故事。
- 每个假说必须有「什么证据能推翻它」，且该证据是否已去找过要明确标注。
- 相关性不得直接表述为因果。因果结论需要显式的因果论证，并标注为【判断】。

**误用**

- ❌ 假说集合由模型自由联想 → 应从已知的机制清单或历史案例中枚举
- ❌ 排第一就当成定论 → 排序表达的是证据强度，不是真值

## 加算子之前先问四个问题

1. 现有算子真的表达不了，还是只是**维度设计得不对**？
2. 这个"新算子"是不是两个现有算子的**组合**？
3. 它是数学性质的（折叠方式）还是业务性质的（某个领域的习惯）？**业务性质的东西不该进算子集，该进任务包。**
4. 它是不是某个现有算子的**退化形态**？（`diff` 就是这么被并进 `trend` 的）
