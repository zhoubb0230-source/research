# 平台落地映射

专家团设计为平台中立。`pipeline.yaml` 用「阶段 + 契约 + 准入条件」描述，本文说明如何落到具体平台。

## 选型验收：三条硬性能力

任何候选平台按此验收，**第 3 条做不到的平台不能选**。

| # | 能力 | 为什么是硬性的 |
|---|---|---|
| 1 | **阶段间硬门**：准入条件不满足不得放行，且无人工旁路 | 没有硬门，两段式筛选退化成一次性打分 |
| 2 | **证据库跨阶段持久化**，`evidence_id` 全局唯一 | 证据库是唯一真相源，散在各会话上下文里就不成立 |
| 3 | **渲染前的确定性校验钩子**，非 0 退出码即阻断 | 第三道闸是唯一不可被模型绕过的防线 |

## 四类平台映射

### A. 本方数字员工平台（`agent-platform-solution-0001`）— 推荐

| pipeline 概念 | 平台对应 |
|---|---|
| 阶段 | L2 BPMN 流程引擎的子流程 |
| 准入条件 | BPMN 网关 |
| 人工签署（P0/P9） | BPMN 人工任务 |
| 角色 | L3 运行时的 Skill 装配 |
| 证据库 | L5A 知识层 |
| 外部检索 | L4 网关统一出口 |
| 校验钩子 | P8 出口网关上的服务任务 |

**优势**：证据库天然获得权限管控与审计留痕；流程引擎是状态真相源，整轮可重放；P5 的 2 轮上限用流程计数器强制，不依赖模型自觉。
**代价**：需要平台本身已具备生产可用度。

### B. Dify / Coze Studio 类工作流平台

| pipeline 概念 | 平台对应 |
|---|---|
| 阶段 | 工作流节点 |
| 准入条件 | 条件分支 |
| 角色 | 各自独立的 Agent 应用 |
| 证据库 | 外部数据库 + 自定义工具 |
| 校验钩子 | 自定义代码节点 |

**注意点**：
- 循环与迭代能力需实测。P3（采集↔核证）与 P5（2 轮对抗）都需要受控循环。
- 2 轮上限必须建**显式计数器**，不能靠提示词约束。
- 结构化输出的严格程度需验证——schema 强制是防编造第一道闸，弱校验等于没有。

### C. LangGraph 类代码编排

| pipeline 概念 | 平台对应 |
|---|---|
| 阶段 | StateGraph 节点 |
| 准入条件 | 条件边 |
| 证据库 | 图 state + 外部持久化 |
| 校验钩子 | 节点内直接调用 `verify_report.py` |

**优势**：灵活度最高，三条硬性能力都容易满足。
**代价**：运维成本最高，没有现成的流程可视化与人工任务。

### D. Claude Managed Agents

| pipeline 概念 | 平台对应 |
|---|---|
| 阶段 | 每阶段一个 Session |
| 角色 | 版本化的 Agent 配置（创建一次，按 ID 引用） |
| S2 并行 | 多智能体 roster 派发给 worker |
| 证据库 | 会话工作区 + Files |
| 校验钩子 | 沙箱内执行 |

**注意点**：编排逻辑较薄，**阶段间的硬门需要在客户端代码里守住**——平台不会替你拦。这一点若省略，整个两段式结构会失效。

## 与承载平台无关的三件事

无论选哪个平台，以下三项都在平台之外维护，不要下沉到平台配置里：

1. **`rubric-vN.yaml`** —— 口径是业务资产，需要独立版本化与评审。
2. **`schemas/*.json`** —— 契约先于实现。
3. **`checks/verify_report.py`** —— 校验逻辑不能是平台的一个节点配置，它必须是可独立运行、可独立测试的脚本。
