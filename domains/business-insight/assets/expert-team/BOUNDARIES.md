# 专家装配的三层边界

> 本文回答一个问题：**同一句话，应该写进配置、写进人格文件，还是写进技能？**
>
> 结论先说：不是两层，是**三层**。把"能提到专家配置的都提到专家配置"当成一条规则会出错，
> 因为"专家配置"本身跨了两个性质完全不同的层——一层是运行时强制的，一层是每轮花钱注入的散文。

---

## 一、三层是什么

| 层 | 载体 | 谁执行 | 成本 | 违反的后果 |
|---|---|---|---|---|
| **T1 配置层** | OpenClaw `agents.entries.<id>`；dsh provider 路由 + preset + `spawnTeammate` 实参 | **运行时** | 零 token | 做不到——路根本不存在 |
| **T2 人格层** | `IDENTITY.md` / `SOUL.md` / `AGENTS.md` / `USER.md`；dsh 的 `spawnTeammate(prompt)` | 模型自觉 | **每轮全文注入** | 模型可能不遵守 |
| **T3 技能层** | `skills/<name>/SKILL.md` | 模型按需调用 | 提示词里只占 name + description（OpenClaw 实测约 97 字符 + 字段长度） | 模型可能不去调用 |

三层的判据各不相同，**依次判定，命中即停**：

```
这句话能表达成运行时的配置字段吗？ ── 能 ──→ T1（必须放 T1，不允许只写在散文里）
              │ 不能
              ↓
它是不是每一轮推理都要用到的判断底色？ ── 是 ──→ T2
              │ 不是（只在某个动作里用）
              ↓
                                             T3
```

---

## 二、T1：能配置的，必须配置

**这一条比"优先提取到专家配置"更强：不是优先，是必须。**

散文是**请求模型自觉**，配置是**运行时不给这条路**。两者不是同一种东西的强弱版本，
是"承诺"与"机制"的区别。凡是能落到配置字段的约束，只写在提示词里就等于没有约束。

本方案中被从散文搬到 T1 的约束：

| 原来写在提示词里的话 | 现在落在哪 | 变成了什么 |
|---|---|---|
| "你必须与分析师使用不同模型" | `entries.red-team-challenger.model` / dsh 独立 provider 路由 | 异源由装配保证，不由自觉保证 |
| "你不看分析师的推理过程" | `sessions_spawn(context: "isolated")` / `spawnTeammate(context: 'fresh')` | 平台保证子会话是干净 transcript |
| "报告生成专家不得执行命令绕过发布闸" | `entries.report-writer.tools.deny: ["exec", ...]` | 工具不在它的有效工具表里 |
| "报告生成专家只能写自己的工作区" | `entries.report-writer.sandbox.mode: "all"` | 写不到发布目录 |
| "总调度不得自己写 rubric" | `entries.chief-coordinator.tools.deny` + 只有它有 `subagents.allowAgents` | 它没有内容产出所需的工具面 |
| "数据采集专家不得自行并入新对象" | 它不在任何人的 `allowAgents` 里，且 dsh 名册是扁平的 | 它无法派人、无法改上游产物 |
| "每位专家用哪个档位的算力" | `thinkingDefault` / provider 的 `reasoningEffort` | 装配即定，不靠提示词自述 |

> ⚠️ **反向的坑**：T1 强，但**只在平台真的支持这个字段时才强**。
> 把一条约束写进一个平台不认识的字段，是最坏的情况——配置层静默失效，而你以为它被强制了。
> 两个平台各自的「哪些字段是文档明确的、哪些是我推断的」，见 `../expert-team-openclaw/OPENCLAW-NOTES.md`
> 与 `../expert-team-dsh/DSH-NOTES.md`，两份都单列了上线前必须校验的清单。

## 三、T2 与 T3：这里要反驳"能提取的都提取到配置"

**T2 和 T3 之间的分界不是重要性，是"每一轮要不要"。**

把内容尽量往 T2（人格文件）搬，在这两个 harness 上都会直接付出代价：

- OpenClaw 的 bootstrap 文件是**每轮全量注入**系统提示词的，单文件默认上限
  `bootstrapMaxChars: 20000`、合计 `bootstrapTotalMaxChars: 60000`，**超出即截断**。
  运行时只会说"有文件被截断了"，不告诉你截了哪个、截了多少——
  而被截掉的总是文件末尾，也就是"我绝不做的事"那一段。
- dsh 的 teammate 人格走 `spawnTeammate(prompt)`，整段进入该 Session 的提示词前缀，
  同样是每轮都在。

> **一处更正**：本仓库早先的 `OPENCLAW-NOTES.md` 说洞察总调度的 `AGENTS.md`「约 18 KB，
> 逼近 20000 上限」。那是**拿 UTF-8 字节数去比一个字符数上限**——中文一字三字节，
> 实测旧装配是 7824 **字符**（约 20 KB 字节），离 20000 字符还有一半余量。
> 截断风险当时被高估了。
>
> 但 T2/T3 要拆这件事本身不受影响，因为真正的理由不是"会不会截断"，
> 而是**每轮都在花钱**：那 7824 字符里有 6000 多字符是只在推进状态时才用得上的流程表，
> 却在这位专家的每一轮推理里被重新注入一遍。

而技能是**懒加载**的：两个平台都只把 `name` 与 `description` 放进提示词目录，正文在被调用时才读。
OpenClaw 文档给的量化是每个技能约 97 字符 + 字段长度（约 24 token）；
dsh 的模型侧目录同样"只用 name 和 description，从不用正文"。

所以判据是：

| 内容性质 | 放哪 | 例子 |
|---|---|---|
| **判断底色**——每一轮推理都要压着的立场、KPI、禁令 | T2 | "你的 KPI 是推翻数，一轮什么都没推翻是失职" |
| **交接契约**——我吃什么、吐什么、给谁、schema 是哪个 | T2 | "我的产出必须过 `verdict.schema.json`" |
| **操作流程**——只在我负责的那个动作里才用到的步骤、清单、判定表 | **T3** | 证伪的十类质疑归类表、取证的六步、核证的四态判定 |
| **长表格、来源清单、锚点表** | **T3** | 枚举的八类目录来源、口径陷阱清单 |

**具体到本方案，最典型的一处修正**：洞察总调度原先把 220 行的运行手册直接拼进它的
`AGENTS.md`，装配后 **7824 字符**。现在手册变成技能 `skills/run-insight-batch/`，
`AGENTS.md` 只留"什么时候去读这本手册"，降到 **1001 字符**。

拆完之后，12 位专家的人格层（`IDENTITY` + `SOUL` + `AGENTS` + 护栏 + `USER`）
实测在 **3629–4072 字符**之间，全部落在 60000 字符的合计预算的 7% 以内。
判断留在 T2，流程搬进 T3。

## 四、一句话怎么落层：可操作的检验

写下一句约束时，依次问：

1. **"如果模型决定不听这句话，会发生什么？"**
   - 答"它做不到" → 已经在 T1，对。
   - 答"它就那么做了，而且没人会发现" → **这句话必须搬到 T1**。搬不了就说明平台缺这个能力，
     该在 NOTES 的待校验清单里记一笔，而不是假装写在提示词里就算数。
2. **"这句话在这位专家不干活的那些轮里，有用吗？"**
   - 没用 → T3。
   - 有用（它在约束这位专家怎么想） → T2。
3. **"这句话有多长？"**
   - 超过约 40 行还落在 T2 → 大概率是流程混进了立场，拆开：立场留 T2，步骤进 T3。

## 五、两个 harness 的层能力差异（这决定了同一句话在两边落点不同）

| 能力 | OpenClaw | DeepSeek Harness |
|---|---|---|
| 逐专家模型 | ✅ `entries.*.model` | ✅ `spawnTeammate(provider)` 选已注册路由 |
| 逐专家思考档 | ✅ `entries.*.thinkingDefault`（`off`…`xhigh`/`max`/`adaptive`） | ⚠️ 只能靠**每档一条 provider 路由**间接给（`reasoningEffort` 是 provider 级） |
| 逐专家工具面 | ✅ `entries.*.tools.{profile,allow,deny}` | ❌ **队友共用 Lead 的组合**，无法逐队友收窄 |
| 逐专家沙箱 | ✅ `entries.*.sandbox` | ❌ 同上；且队友共享同一 cwd |
| 逐专家技能白名单 | ✅ `entries.*.skills`（空数组 = 无技能） | ❌ 目录是共用的；"该用哪个技能"只能写进 T2 |
| 逐专家人格文件 | ✅ 各自 workspace 的 `IDENTITY/SOUL/AGENTS/USER/MEMORY` | ⚠️ 只有一个通道：`spawnTeammate(prompt)`；`AGENTS.md` 按**目录**加载，队友共享 cwd 因此无法区分 |
| 上下文隔离 | ✅ `context: "isolated"`（默认） | ✅ `context: 'fresh'`（无父历史种子） |

**结论**：OpenClaw 侧尽量把约束压到 T1；dsh 侧的工具与技能约束**压不下去**，
只能留在 T2 并接受"这是承诺不是机制"——这一点必须在 dsh 的 NOTES 里显式写明，
不能让人误以为两边强度一样。dsh 侧真正的机制闸是**发布脚本**与 **preset 组合本身**
（整个团队能用什么工具由 preset 决定，只是无法逐人区分）。
