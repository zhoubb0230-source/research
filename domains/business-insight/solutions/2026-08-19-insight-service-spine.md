# 洞察服务的统一骨架与任务包规范

> **面向**：把业务洞察从一次性需求做成内部可复用服务
> **交付**：`../assets/insight-service/`，含骨架规范、任务包 Schema、聚合算子集、两份验证用预设、校验器
> **标记约定**：【设计】设计主张；【判断】推断
> **状态说明**：`draft`。抽象已用两份差异极大的预设做过表达性验证（均通过 Schema 与跨字段校验），但**尚未跑过任何一轮真实洞察**。角色去耦尚未执行，见 §6。

## TL;DR

- **不要列范式清单。** 每来一个新需求就补一条范式，那不是抽象是待办列表，而且永远补不完。
- **差异是退化，不是缺失。** "单标的评估没有枚举阶段"是错的——它的枚举退化成了 n=1；"格局测绘没有排序"也是错的——它的聚合算子从排序换成了矩阵。
- **一条骨架（九动作）+ 参数化任务包。** 新需求 = 新任务包，不是新流程。
- **范式降级为预设，不是类型。** 类型加一个要动架构所以必须收敛；预设加一份 JSON 即可，加错了删掉。
- **后五个动作永不退化**：取证、核证、证伪、仲裁、成文。任何"为了快一点"而跳过其一的档位设计都是错的。

---

## 1. 问题：范式枚举法不收敛

设计过程中先后被要求覆盖：新业务机会筛选 → 某类工具的业界现状 → 以及"洞察需求可能有很多种"。

每次的应对都是往范式清单里加一条。第三次时问题暴露了：**用户说的是"各类洞察需求"，而枚举法产出的是一个有限清单**。二者不可能对齐。

把几种差异极大的需求拆开对比：

| 需求 | 对象集合从哪来 | 聚合成什么 |
|---|---|---|
| 新业务机会筛选 | 产业目录穷举 | 加权排序 |
| 某类工具的业界现状 | 穷举 + 过程中发现 | 特征矩阵 + 路线分组 |
| 该不该自研某能力 | 需求方给定的几个选项 | 单一结论 |
| 某指标为什么下滑 | 候选解释假说 | 按证据支持度排序 |
| 季度跟踪竞对动态 | 上一批次的基线 | 与基线比对 |

**中间的取证、核证、刻画、证伪、仲裁、成文一模一样。** 差异只有首尾两处。

## 2. 解法：统一骨架 + 参数化

### 2.1 九个动作

```
① 界定 → ② 枚举 → ③ 取证 ⇄ ④ 核证 → ⑤ 刻画 → ⑥ 聚合 → ⑦ 证伪 → ⑧ 仲裁 → ⑨ 成文
```

完整契约见 `../assets/insight-service/spine.md`。

### 2.2 可退化的四个与永不退化的五个【设计】

| | 动作 | 说明 |
|---|---|---|
| **可退化** | ① 界定 ② 枚举 ⑤ 刻画 ⑥ 聚合 | 需求已结构化则跳过界定；对象给定则跳过穷举；无维度则刻画退化为事实摘录；单对象则聚合即结论 |
| **永不退化** | ③ 取证 ④ 核证 ⑦ 证伪 ⑧ 仲裁 ⑨ 成文 | **方法论内核。** 没有取证核证 = 产出模型记忆；没有证伪 = 确认偏误放大器；没有成文闸 = 编造数字流到报告 |

**这是本规范最重要的一条。** 快速档可以缩小取证广度、把证伪压到 1 轮，但不能取消任何一个动作。

### 2.3 退化必须显式暴露

每次退化记进 `degradations[]`，并在报告首屏呈现（"本次未做穷举枚举，不保证覆盖完整"）。
与"数据缺失必须显式暴露"同一原则：**降级必须可见。**

## 3. 任务包：八组参数

| 组 | 承载什么 | 退化取值 |
|---|---|---|
| `decisionQuestion` | **这份洞察支持什么决策**（必填） | 无——答不上的多半是检索需求，应在分诊拦下 |
| `subject` | 对象单位、边界（含/排）、集合来源、基数 | 来源 = given |
| `criteria` | 维度（带类型）+ 闸门（带触发时机） | 维度为空 = 兜底档 |
| `aggregation` | 聚合算子，**可组合** | `verdict` |
| `evidencePolicy` | 等级实例清单、最低入表等级、**最大证据年龄**、可否直接验证 | 沿用默认等级 |
| `temporal` | 时点、回溯窗口、前瞻窗口、报告有效期 | 全空 |
| `output` | 模板、读者、深度档位、归档目录 | 默认模板 |
| `domainPack` | 术语表、数据源、已知陷阱 | 空 |

### 3.1 一种 rubric，维度带类型【设计】

先前判断"rubric 有打分型与特征型两种，要分别支持"——**这个判断是错的，已修正**。
一种 rubric 即可，维度带 `type` 字段：

- `ordinal` 可打分排序（需锚点，参与 `rank` 时需权重）
- `categorical` 取值域，用于分组
- `factual` 事实字段
- `temporal` 时序，用于趋势与变化

打分型 = 维度全是 `ordinal` 且有权重；特征型 = 以 `categorical` 为主。**不需要两套 schema。**

### 3.2 证据等级：骨架通用，实例清单领域专属【设计】

A/B/C/D 的等级机制在方法论层（不变），**每级的实例清单在任务包层**（每次变）。
产业数据的 A 级（官方统计、海关、年报）与软件工具的 A 级（官方文档、changelog、开源仓库、可复现基准）不是一回事。

**新增一档：直接验证。** 软件类对象可以真的跑一下、读源码、调 API——这比任何二手来源都强。
产业机会洞察拿不到这种证据（没法"跑一下"一个设备市场）。
**这意味着本系统在技术类洞察上会比在产业洞察上明显更可靠**【判断】。

## 4. 聚合算子集

六个，刻意保持收敛。契约见 `../assets/insight-service/aggregators.md`。

| 算子 | 输入要求 | 输出 |
|---|---|---|
| `rank` | ≥1 ordinal 维度 + 权重和为 100 | 排序榜单，先按置信度分层 |
| `matrix` | ≥2 维度 | 对象×维度矩阵 + 关键差异点 |
| `cluster` | ≥1 categorical 维度 | 分组 + 组间边界说明 |
| `verdict` | 任意 | 结论 + 依据 + **反方论证** |
| `diff` | baseline 来源 | 变化清单（含"未变"） |
| `rank_hypotheses` | 假说集合 | 解释排序 + **保留竞争解释** |

**算子是数学性质的（怎么折叠矩阵），不是业务性质的。** 业务差异由维度与判据表达。
加算子前先问：现有算子真表达不了，还是维度设计得不对？是不是两个算子的组合？

## 5. 验证：两份差异极大的预设

抽象的唯一检验标准是**能不能表达真实需求**。用两份取值几乎完全不同的预设做了验证：

| | `opportunity-screening` | `landscape-survey` |
|---|---|---|
| 对象单位 | 业务机会 | 产品/工具 |
| 集合来源 | 产业目录穷举（7 个目录） | 目录穷举 + 过程发现 |
| 维度类型 | 6 个 ordinal，带权重 25/18/20/15/12/10 | 6 个 categorical + 1 ordinal + 3 factual + 1 temporal |
| 闸门 | 6 条（4 条前置 / 2 条后置） | 3 条 |
| 算子 | `rank` + 三个修正项 | `cluster` + `matrix` |
| 证据 A 级 | 官方统计、海关、年报、招股书 | 官方文档、changelog、开源仓库、可复现基准 |
| 最大证据年龄 | 24 个月 | **6 个月** |
| 可直接验证 | 否 | **是**（安装试用、读源码、调 API） |
| 输出模板 | 榜单模板 | **仓库既有的 `templates/insight.md`** |

两份均通过 JSON Schema 与跨字段校验。**原始的「经纬线 a–f」六条判据被完整表达为 `opportunity-screening` 预设的 6 个 ordinal 维度 + 3 个修正项 + 6 条闸门**，没有丢失信息。

校验器对故意写坏的任务包报出 13 项错误 + 4 项提示（算子与维度不匹配、闸门依赖不存在的维度、以数据可得性为由 reject、领域维度但 domainPack 为空等）。

## 6. 实施进度

### 6.1 已完成（2026-08-19 修订）

| 项 | 说明 |
|---|---|
| **⑨ 解读动作** | 新增为独立动作，排在仲裁之后成文之前；三分法（可直接借鉴/需验证再决策/明确不做）+ 四条护栏；`interpretation.ourContext` 承载我方处境 |
| **回边 R1 发现回路** | 取证发现新对象 → 走闸门后并入，触发全局重算 |
| **分诊拒绝路径** | ① 界定的终止出口，三问判定，拒绝是正常终局 |
| **基线快照** | ⑩ 成文的第二产物 `baseline.json`，跨 brief 版本不可比对 |
| **`trend` 吸收 `diff`** | `diff` 是 `trend` 在 n=2 时的退化形态。算子从六个收敛到五个 |
| **回环模型** | 质疑类型路由表、返工预算与单调收敛、全局重算与 Top K 缓冲带、"只回不进"铁律 |

## 7. 连带修正的既有判断

| 原判断 | 修正 |
|---|---|
| "P1 枚举在单标的评估里根本不存在" | 错。它退化成 n=1，**退化不是缺失** |
| "rubric 有两种形态，要分别支持" | 错。一种 rubric，维度带类型即可 |
| "应支持 N 种洞察范式" | 范式是**预设**不是**类型**；类型只有一个 |
| "用户输入需求、选择相关专家" | 专家班底由骨架决定，对所有需求相同。用户只需选领域包与是否启用合规专家 |
| "骨架是线性九步" | 错。有五条回边，是带回边的 DAG。最需要回环的路径（证伪发现证据不足）原本恰恰没有 |
| "`diff` 是独立算子" | 错。它是 `trend` 在 n=2 时的退化形态——违反了本骨架自己的"退化不是缺失"原则 |

## 8. 开放问题

| 问题 | 阻塞什么 | 决策人 |
|---|---|---|
| 骨架抽象是否成立 | 后续全部工作 | 需评审本方案 §5 的验证是否充分 |
| 预设该由谁维护 | 服务可持续性 | 建议由提需求的业务方写，平台只给模板与评审 |
| 领域包的维护责任 | 最大的运营风险【判断】 | 同上；且需版本化 + 标注最后核对日期，过期包在报告上打标记 |
| 首个真实跑通的需求选哪个 | MVP 验证效率 | 建议 `landscape-survey`——你们自己是专家，报告出来五分钟就知道靠不靠谱，且产出可直接入 `domains/ai-coding/insights/` |
