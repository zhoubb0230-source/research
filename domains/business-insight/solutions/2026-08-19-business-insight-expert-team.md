# 业务洞察专家团：多智能体产业机会洞察系统设计方案

> **面向**：以半导体装备技术链为基座，系统化搜寻并评估新业务/新机会的产业洞察工作
> **形态**：一套运行在多 Agent 协作平台上的专家团，输入是经纬线口径，输出是可排序的机会榜单与逐机会的深度洞察报告
> **标记约定**：【设计】为本方案的设计主张；【判断】为基于工程经验的推断，非事实；【待定】为需要业务侧输入才能定稿的参数
> **状态说明**：`draft`。本方案是系统设计与可运行资产，**尚未运行过任何一轮真实筛选**。文中所有权重、阈值、成本数字均为初始建议值或参数化测算口径，不是实测结论。文中不含任何未经核实的产业数据——按设计原则，产业数据只能由专家团在运行时带来源产出。

## 0. 对原始构想的评估

原始构想给了两块内容：**角色规划**与**洞察步骤（经纬线 a–f）**。整体方向成立，但有五处会在落地时致命，需要改。

### 0.1 成立的部分

| 构想 | 评估 | 说明 |
|---|---|---|
| 采集 / 分析 / 审查 / 生成 四类角色 | ✅ 成立 | 对应洞察工作的真实工序，不是为了多智能体而多智能体 |
| 显式设"质疑审查"角色 | ✅ 关键正确 | LLM 洞察最容易死在附和与确认偏误上，对抗角色是刚需 |
| 设"调停"角色 | ✅ 成立 | 有对抗就必须有裁决，否则分歧会以"折中"的形式污染结论 |
| 每角色配不同模型 | ✅ 成立 | 各角色的能力需求差异极大（广度/推理/核对/渲染），同一模型全用是浪费也是低效 |
| 经纬线 a（技术链重合） | ✅ 且应为最高权重 | 能力可迁移性是多元化成功率最强的预测因子 |
| 经纬线 f（过了泡沫破灭期） | ✅ 逻辑成立 | 逆向选择：估值与竞争都处于低点，但技术仍在推进 |
| 显式要求"禁止编造数据" | ✅ 必须 | 但**仅靠指令做不到**，见 0.2 第 ① 条 |

### 0.2 必须修改的五点【设计】

**① "禁止编造数据"是架构问题，不是提示词问题。**
把"不许编"写进每个角色的提示词，只能降低概率，不能归零。真正的根因是**"必须把表格填满"的结构性压力**——评分卡有 6 个维度、每个维度要数字，模型找不到就会给一个"看起来合理"的数。
解法有三条，缺一不可：
1. **让留白合法且不受惩罚**：评分卡显式支持 `NA`，缺数据不扣分，只降低该机会的结论置信度。取消编造的动机。
2. **数字与证据强绑定**：分析角色的输出 schema 里，任何数值字段必须同时携带 `evidence_ref`；无引用的数值在 schema 校验层被拒绝，不进入下一环。
3. **渲染层做确定性拦截**：报告由模板渲染，渲染前用脚本扫描正文里的每一个数字，凡不在证据库中或 `verify_status != verified` 的一律阻断（见 `assets/expert-team/checks/verify_report.py`）。
> 与 `agent-platform-solution-0001` 的判断二同构：**权限不能做在提示词里，真实性同样不能。**

**② 第二阶段不能是"证实"，必须是"证伪"。**
原构想第 2）步写的是"用专家的逻辑去证实新业务的评选因素"。如果给 Agent 的任务是"证实"，它一定能证实——这是确认偏误的定向放大器，而且是本系统最大的失效模式【判断】。
改为：每个进入深度阶段的机会，**先写证伪备忘录**（三条最可能致命的假设 + 推翻各自需要什么证据），再由红队按备忘录攻击，最后才做正向论证。红队的 KPI 是**推翻/降级的机会数**，不是产出字数。

**③ 六条经纬线不能放在同一个加权公式里。**
a（技术链重合）与瓦森纳/出口管制是**门槛**：不满足则再高分也做不了。c/d（规模、格局）是**加权项**。混在一起线性加权，会让"分数很高但我们根本做不了"的机会冒到榜首。
改为**两段式：先过闸（Gate，一票否决）→ 再打分（Score，加权排序）**。详见 `business-insight-solution-0002`。

**④ 机会池的生成方式没定义，这是最大的方法论缺口。**
原构想说"依据经纬线梳理出新的业务/机会"，但没说机会从哪来。如果让模型自由联想，产出的就是它训练语料里的热门词，既有遗漏也有编造。
改为**穷举扫描 + 逐层淘汰**：从可枚举的产业目录自底向上扫（国民经济行业分类、战略性新兴产业分类、十五五规划文本、首台套/攻关目录、行业协会设备目录、进口海关税则章节），先求覆盖，再求筛选。**枚举阶段禁止判断，筛选阶段禁止新增。**

**⑤ "报告生成专家"应当降级为渲染器。**
让一个 LLM 自由撰写终稿报告，等于在流程末端再开一次编造窗口——它会为了行文顺畅补上过渡性的数字和断言。
改为：分析阶段产出**结构化 JSON**，报告由模板确定性渲染；LLM 只负责把结构化字段改写成通顺中文，**且被明确禁止引入任何新数字、新实体、新因果断言**，改写后再过一遍数字校验。

### 0.3 对"是否划分业务领域"的回答【判断】

**第一阶段（筛选）不要按行业拆 Agent；第二阶段（深度洞察）才引入领域能力，且以知识包形式注入，不以人格副本形式复制。**

理由：筛选阶段的全部价值在于**跨行业可比性**。同一把尺子必须由同一个角色（同一提示词 + 同一模型 + 同一 effort）执行，否则"半导体领域专家"和"生物医药领域专家"打出的 7 分不是同一个 7 分，排序失去意义。
深度阶段确实需要领域知识，但正确形态是给同一个分析师角色挂载**领域知识包**：术语表 + 数据源清单 + 该领域的技术链图谱 + 已知陷阱清单。知识包是数据，可版本化、可评审、可复用；人格副本是提示词分叉，会不受控地漂移。

### 0.4 补充的三条经纬线维度

原构想 a–f 覆盖了"值不值得做"，缺了"我们能不能进去"。补三条（详见 solution-0002）：

- **g. 进入路径可得性**：是否存在可并购标的 / 可获取的关键团队 / 愿意联合开发的灯塔客户。没有进入路径的机会不是机会，是新闻。
- **h. 验证成本与周期**：首台套 NRE、客户验证周期。装备类业务的隐性成本主要在这里，且它决定了试错次数。
- **i. 管制不对称性**：在位者受出口管制限制的程度。这一条与 d（竞争格局）强耦合——**两强格局 + 两强均受对华管制**，是最好的机会而不是最差的。

### 1.1 四条架构铁律【设计】

1. **证据库是唯一真相源。** 任何角色不得在自己的输出里"记得"一个数字。数字只能来自证据库，通过 `evidence_ref` 引用。角色可以提出"需要某个数"，由采集官去取。
2. **枚举与判断分离。** P1 只负责覆盖不负责淘汰，P2 只负责淘汰不负责新增。混在一起会同时产生遗漏和编造。
3. **对抗角色必须换模型、换会话、换视角。** 同一模型对自己刚写的内容做批判存在同源盲区【判断】，自我批判的发现率显著低于异源批判。红队不读分析师的推理过程，只读结论与证据。
4. **管制判定必须回原文。** 出口管制清单、十五五文本、行业分类目录，一律现场检索原文并给出定位（章节/条目号），**禁止凭模型记忆作答**。这类内容更新频繁且模型记忆易错位，是编造的高发区。

## 2. 角色设计

12 个角色分四组。**MVP 只需其中 8 个**（标 ★），其余在第二轮迭代引入——角色数量的边际收益递减很快，先跑通再扩【判断】。

### 2.1 G 组 · 治理与口径

| ID | 角色 | 职责 | 关键约束 | MVP |
|---|---|---|---|---|
| G1 | 总编排官 | 流程状态机、阶段准入/终止条件、预算与并发控制、失败重试 | **不产出任何内容判断**。建议直接用编排引擎实现，不用 LLM | ★ |
| G2 | 口径官 | 把经纬线 a–i 翻译成可计算指标、打分锚点、数据源等级；维护 `rubric-vN` | 口径是**唯一真相源**且**版本冻结**：一轮筛选中途不得改口径，改则整轮重跑 | ★ |

### 2.2 S 组 · 正向（枚举、取证、分析）

| ID | 角色 | 职责 | 关键约束 | MVP |
|---|---|---|---|---|
| S1 | 机会枚举官 | 从产业目录自底向上穷举候选池，输出候选清单 + 来源目录定位 | **禁止价值判断**，禁止"我觉得这个不行"就不列。覆盖率优先，宁滥勿缺 | ★ |
| S2 | 证据采集官（×N 并行） | 按指标清单定向取证，产出**证据卡**而非结论 | 输出必须是证据卡 schema；找不到就写 `not_found`，**禁止估算、禁止外推、禁止用"约/预计/业内普遍认为"填充** | ★ |
| S3 | 产业分析师 | 在证据卡之上做评分与理由，产出结构化评分 JSON | 只能引用证据库；每个分值必须写明命中了锚点表的哪一档 | ★ |
| S4 | 技术链分析师 | 专管 a（能力重合度）与 f（技术成熟度/国产化缺口），挂载半导体装备领域知识包 | 重合度必须拆到子能力项（真空/精密运动/光机电/超净/射频电源/量测/控制软件/可靠性工程）逐项判定，不给整体印象分 | ★ |

### 2.3 C 组 · 质疑（对抗与核证）

| ID | 角色 | 职责 | 关键约束 | MVP |
|---|---|---|---|---|
| C1 | 红队 / 证伪官 | 对每个机会写"最可能错在哪"，主动找反例与致命假设 | **换模型、换会话**；只看结论与证据，不看分析师的推理链；KPI 是推翻/降级数 | ★ |
| C2 | 数据核证官 | 逐条回源核对数字与来源，判定证据等级与 `verify_status` | 硬闸门。`locator` 必须能定位到具体页/表/条目，否则判 `unverified` | ★ |
| C3 | 合规与管制官 | 出口管制（瓦森纳/EAR/两用物项）、准入资质、法律红线的**双向**判定 | 一律回原文检索并给定位；双向判定见 §4 | ★ |

### 2.4 A 组 · 调停与输出

| ID | 角色 | 职责 | 关键约束 | MVP |
|---|---|---|---|---|
| A1 | 仲裁官 | 裁决 S 组与 C 组的分歧，产出裁决记录 | **按证据等级裁决，不投票、不取中值**；分歧未解则降低置信度并显式标注 | ★ |
| A2 | 首席洞察官 | 只把关"结论对决策有没有用"：是否可执行、是否有区分度、是否只是常识复述 | 有权打回重做，无权修改数据 | ☐ |
| A3 | 报告渲染器 | 模板渲染 + 文字改写 + 数字校验 | **禁止引入任何新数字、新实体、新因果断言**；渲染后必过 `verify_report.py` | ☐ |

> MVP 阶段 A2/A3 由人工承担：8 个角色跑通一轮，人工读榜单和报告，把发现的问题回灌成 A2/A3 的提示词。**先有人工基线，再自动化**【设计】。

### 2.5 被刻意排除的角色

| 未设 | 原因 |
|---|---|
| 按行业拆的 N 个"领域专家" | 破坏跨行业可比性，见 §0.3 |
| "创意/头脑风暴专家" | 机会来自目录穷举，不来自联想。联想是编造的入口 |
| "投票委员会" | 多数票会让弱证据结论通过。裁决按证据等级，不按票数 |
| 独立的"报告撰写专家" | 见 §0.2 ⑤，末端自由写作是二次编造窗口 |

## 3. 模型配置

模型能力档位与角色需求的映射【设计】。价目为 Claude API 首方费率（输入/输出，美元/百万 token，口径日期 2026-06-24），第三方云平台费率不同。

| 角色 | 模型 | effort | 关键能力需求 | 选型理由 |
|---|---|---|---|---|
| G1 总编排官 | 不用模型（编排引擎） | — | 确定性 | 状态机用代码写，比用模型稳定且免费 |
| G2 口径官 | `claude-opus-5` | `high` | 强推理、指标设计 | 一轮只跑一次，成本可忽略，质量决定整轮上限 |
| S1 枚举官 | `claude-opus-5` | `medium` | 产业常识广度、长上下文 | 需要读完整目录文本（1M 上下文）；判断负担轻，`medium` 足够 |
| S2 采集官 ×N | `claude-sonnet-5` | `medium` | 长文档抽取、Web 检索 | 量最大的角色，成本敏感；1M 上下文可整篇吃研报/年报。**不用 Haiku 4.5**：200K 上下文在整本年报上会被迫截断，抽取失真 |
| S3 产业分析师 | `claude-opus-5` | `xhigh` | 强推理、结构化输出 | 评分一致性直接决定排序可信度，这里不省钱 |
| S4 技术链分析师 | `claude-opus-5` | `xhigh` | 强推理 + 领域知识包 | 同上；a 是最高权重维度 |
| C1 红队 | `claude-fable-5` | `max` | 最强推理、异源 | **必须与 S3 异源**以规避同源盲区【判断】。预算受限时退而求其次：同为 opus-5 但换提示词范式 + 换会话，效果次之 |
| C2 数据核证官 | `claude-sonnet-5` | `medium` | 机械核对、Web 取回 | 高频低难度，纯核对不需要 opus 档 |
| C3 合规管制官 | `claude-opus-5` | `high` | 强推理 + 原文检索 | 低频、高风险、错判代价大 |
| A1 仲裁官 | `claude-opus-5` | `xhigh` | 强推理、证据权衡 | 裁决质量决定分歧的处置是否合理 |
| A2 首席洞察官 | `claude-fable-5` | `max` | 最强判断力 | 低频；"这个结论有没有用"是最难的判断 |
| A3 渲染器 | `claude-haiku-4-5` | — | 文字改写 | 只做措辞改写，不做判断；数字由脚本把关。成本最低档 |

### 3.1 必须开启的 API 能力

| 能力 | 用于 | 说明 |
|---|---|---|
| 结构化输出 `output_config.format` | S2/S3/S4/C1/C2/C3 | **防编造的第一道闸**：schema 强制数值字段与 `evidence_ref` 同时存在 |
| 严格工具 `strict: true` | 所有工具调用 | 保证 `tool_use.input` 严格符合 schema |
| Web 检索/取回服务端工具<br>`web_search_20260209` / `web_fetch_20260209` | S2 采集官、C2 核证官、C3 合规官 | 取证与回源核对的主力；C3 的原文检索强依赖 |
| 自适应思考 `thinking: {type:"adaptive"}` | S3/S4/C1/A1/A2 | 分析与对抗类角色默认开启 |
| 提示词缓存 | 全部角色 | 口径表、锚点表、领域知识包是稳定前缀，应放在缓存断点之前；候选机会等易变内容放在断点之后 |
| 批处理 API | S1 枚举、S2 首轮粗采 | 非实时环节走批处理，费率减半 |

### 3.2 成本测算口径【测算，非实测】

**不给总额结论**——总额完全取决于候选池规模与研报篇幅，这两个数字在跑第一轮之前谁都不知道。给公式与需要业务侧填的参数：

```
单轮成本 ≈ Σ_角色 [ (输入token × 单价in) + (输出token × 单价out) ]

其中主导项是 S2 采集官：
  S2 成本 ≈ 候选数 N × 每候选指标数 M × 每指标平均取回文本量 T × 单价in
```

【待定】需要业务侧确认的参数：候选池目标规模 N（建议首轮 150–300，覆盖优先）、进入深度阶段的 Top K（建议 5–8）、单机会深度洞察的取证预算上限。

控成本的三个杠杆，按性价比排序【设计】：
1. **闸门尽量前置**：P2 用零成本的规则闸（如"是否在管制清单"）先砍掉大头，再进入昂贵的 P3 取证。闸门顺序错了，成本差一个量级。
2. **S2 用 Sonnet + 批处理 + 缓存**：这一个角色占单轮成本的大头。
3. **深度阶段严格限 Top K**：K 从 5 涨到 15，深度阶段成本涨 3 倍而决策价值几乎不变【判断】。

## 4. 出口管制与合规的双向判定【设计】

原构想把瓦森纳写成"要注意的限制"，这是**单向**理解。管制对新业务评估的作用是**双向**的，必须拆成两个独立字段分别判定：

| 方向 | 问题 | 结果 | 作用 |
|---|---|---|---|
| **向内**（机会侧） | 在位供应商是否受对华出口管制？国内是否存在因此产生的供给缺口？ | 受限程度越高 → **加分** | 这是"国产替代"机会的本体 |
| **向外**（我方侧） | 我方做出来的产品是否落入管制清单？是否影响海外交付、供应链采购、技术合作？ | 落入管制 → **减分或一票否决** | 决定业务的天花板与合规风险 |

因此 d（竞争格局）不能独立打分：**"两强格局"在两强均不受限时是最差信号，在两强均受对华管制时是最好信号。** 这是原构想里"有两强的优先级放低"需要打的补丁。

**C3 合规官的强制工作方式**：
- 判定必须给出**清单原文定位**（清单名称 + 版本/生效日期 + 类别号/条目号 + 检索日期），格式见证据卡 schema。
- **禁止凭模型记忆判定**。管制清单更新频繁、条目编号易错位，是编造高发区。
- 输出三态：`restricted` / `not_restricted` / `undetermined`。**`undetermined` 不允许被下游当作 `not_restricted` 使用**——它会把该机会的置信度打到 `low` 并在报告里显式标红。
- 涉及具体交易与合规结论时，产出只作为**内部研判输入**，最终结论需法务/合规部门确认。本系统不产出合规意见。

## 5. 防编造机制（三道闸）

呼应 `agent-platform-solution-0001` 的"闸门叠加"思路：真实性靠架构，不靠自觉。

### 5.1 闸一 · 产出侧（schema 强制）

所有分析类角色的输出走结构化输出，schema 见 `assets/expert-team/schemas/`。核心约束：

```
任何 number 类型字段  ⟹  必须同时存在同级的 evidence_ref: "EV-xxxx"
任何 evidence_ref     ⟹  必须能在 evidence.jsonl 中命中
数据缺失              ⟹  写 null + status: "not_found"，不写估算值
```

**允许留白且留白不扣分**是本机制成立的前提。若评分卡对 `NA` 扣分，模型就有了编造的动机，schema 只会把编造变成"给一个假的 evidence_ref"。

### 5.2 闸二 · 核证侧（C2 回源）

| 证据等级 | 来源类型 | 可用性 |
|---|---|---|
| **A** | 官方统计与法定披露：统计部门、海关、上市公司年报/招股说明书、政府规划与目录文件、专利数据库 | 可直接支撑结论 |
| **B** | 行业协会与标准组织的公开数据、权威行业年鉴 | 可直接支撑结论 |
| **C** | 券商研究、第三方咨询机构报告 | **需两个独立来源交叉**方可入表，且必须注明机构与发布日期 |
| **D** | 媒体报道、厂商宣传材料、社区讨论 | **永不入表**，只能作为线索去追 A/B 级原始来源 |

C2 的判定输出：`verified`（回源命中且数值一致）/ `conflicting`（多源不一致，需记录全部数值与来源）/ `unverified`（找不到 locator）/ `not_found`。
**只有 `verified` 能进入评分。** `conflicting` 走仲裁；其余降级为 `NA`。

### 5.3 闸三 · 渲染侧（确定性拦截）

`assets/expert-team/checks/verify_report.py`：扫描渲染后的报告正文，提取所有数字，逐个比对证据库。任一不通过则渲染失败，报告不予发布。这一道是**代码，不是模型**——它不会被说服。

## 6. 编排与平台适配

编排定义放在 `assets/expert-team/orchestration/pipeline.yaml`，平台中立，用阶段 + 契约 + 准入条件描述，不绑定任何厂商 DSL。

### 6.1 阶段契约

| 阶段 | 输入 | 输出 | 准入下阶段的条件 | 终止条件 |
|---|---|---|---|---|
| P0 口径固化 | 经纬线原文 + 业务约束 | `rubric-vN.yaml`（冻结） | 人工签署 | 人工确认 |
| P1 枚举 | rubric + 目录来源清单 | 候选清单（含来源定位） | 覆盖率自检通过 | 目录扫完 |
| P2 闸门筛 | 候选清单 | 通过池 + 出局池（含出局理由） | 通过池 ≤ 上限 | 全部候选判定完 |
| P3 取证 | 通过池 + 指标清单 | evidence.jsonl | 核心指标 `verified` 率 ≥ 阈值【待定】 | 预算耗尽或指标取全 |
| P4 评分 | 证据库 + rubric | scorecard.json | schema 校验通过 | 全部候选打分完 |
| P5 证伪 | 评分结果 + 证据库 | 质疑记录 | — | **最多 2 轮**，见下 |
| P6 仲裁 | 评分 + 质疑 | 裁决记录 + 终版榜单 | — | 全部分歧有裁决 |
| P7 深度洞察 | Top K 机会 | 逐机会分析 JSON | 每机会证伪备忘录已闭环 | 逐机会预算上限 |
| P8 渲染 | 分析 JSON + 模板 | Markdown 报告 | **数字校验 100% 通过** | 校验通过 |
| P9 归档 | 报告 | 入库 + 两级索引更新 | 索引已更新 | — |

### 6.2 对抗的终止条件（重要）

多轮辩论的收益递减很快，且无终止条件的对抗会退化成措辞拉锯【判断】。硬性规定：

- **P5 最多 2 轮**。第 1 轮红队攻击，分析师应答；第 2 轮红队只能针对应答中的**新证据**再攻，不得重复第 1 轮论点。
- 2 轮后仍存分歧 → **直接进仲裁**，不再往返。
- 仲裁规则优先级：**证据等级 > 证据数量 > 逻辑一致性 > 保守优先**。
- 仲裁无法裁决时的默认动作是**降低置信度并保留双方结论**，不是取中间值。取中值会制造一个双方都不相信的数字。

### 6.3 平台映射

| 承载平台 | 阶段编排 | 角色 | 证据库 | 备注 |
|---|---|---|---|---|
| **本方数字员工平台**（`agent-platform-solution-0001`） | L2 BPMN 流程引擎，阶段=子流程，准入=网关 | L3 运行时的 Skill 装配 | L5A 知识层 | 首选：证据库天然获得权限与审计；人工签署节点（P0/P9）直接用人工任务 |
| Dify / Coze Studio 类 | 工作流 + 条件分支 | 各角色一个 Agent 应用 | 外部数据库 + API 工具 | 循环与分支能力需实测；P5 的 2 轮限制要显式建计数器 |
| LangGraph 类代码编排 | StateGraph，阶段=节点，准入=条件边 | 节点内调用 | 图 state + 外部存储 | 灵活度最高，运维成本最高 |
| Claude Managed Agents | 每阶段一个 Session；多智能体 roster 承载 S2 并行 | Agent 配置（版本化） | 会话工作区 + Files | 编排逻辑较薄，阶段间的硬门需在客户端代码里守 |

**任何平台上都必须能落地的三件事**，选型时按此验收：① 阶段间的硬门（不满足条件不得放行）；② 证据库的跨阶段持久化与唯一性；③ 渲染前的确定性校验钩子。**做不到第③点的平台不能用**——第三道闸是唯一不可被模型绕过的防线。

## 8. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **模型编造数据** | 结论不可信，且一旦对外汇报后果严重 | 三道闸（§5）；`verify_report.py` 是最后防线；对外汇报只引用 `status: stable` 的条目 |
| **确认偏误：证实而非证伪** | 榜单反映的是模型偏好而非产业现实 | 证伪备忘录前置；红队异源；红队 KPI 按推翻数计 |
| **口径漂移** | 不同批次的分数不可比 | rubric 版本冻结；中途改口径整轮重跑；榜单文件名带 rubric 版本 |
| **数据可得性差**（设备级细分市场规模常无公开权威数据） | 大量维度只能是 `NA`，排序退化 | 承认并显式暴露：榜单必须带"证据覆盖率"列；覆盖率过低的机会标注为"待补证"而非直接排名 |
| **枚举遗漏** | 最好的机会根本没进候选池 | 多目录交叉扫描 + 覆盖率自检；出局池全量留档，可回溯复检 |
| **管制判定错误** | 合规风险 | C3 强制回原文 + 三态输出；`undetermined` 不降级为"无限制"；最终以法务结论为准 |
| **对抗环节无限往返** | 成本失控 | P5 硬性 2 轮上限；仲裁强制收敛 |
| **角色数量膨胀** | 复杂度与成本上升，质量不升 | MVP 只上 8 个角色；新增角色必须先证明现有角色确实覆盖不了 |
| **把系统结论当决策** | 越权 | 本系统产出的是**研判输入**，不是投资决策。所有报告首屏必须带此声明 |
