# 数字员工平台设计方案

> **面向**：可与员工对话协作、可嵌入业务流程节点承担评审等工作的企业级数字员工平台
> **重点**：基于开源组件的运行与管理平台，以及数据隔离与权限管控
> **标记约定**：【业界】为有公开材料支撑的事实，【设计】为基于这些实证做出的方案建议。业界依据详见 `agent-platform-insight-0001`。
> **状态说明**：`draft`。方案尚未经过内部评审与 PoC 验证，其中的容量、时效、阈值等具体数字为初始建议值而非实测结论；所引业界事实的来源核验状态见洞察篇的「待核清单」。

## 0. 结论先行

**判断一：平台的技术难点不是"能不能跑起来一个 Agent"，而是身份、授权、审计三件事。** 编排能力已经是开源商品化组件。

**判断二：数据隔离必须做在架构里，不能做在提示词里。** 权限校验要发生在检索层、在模型之外。任何依赖"提示词里写了不许透露他人数据"的方案，在红队测试下都会失效。

**判断三："用户问到他人数据"的根因，多数不在 AI，而在源系统里早已存在的过度共享。** 数字员工平台只是把这些历史权限债务变得"可被一句话问出来"。因此**数据治理必须前置，不能与平台建设并行**。

**判断四：开源选型应当"分层组装"，而不是"选一个平台包打天下"。** 让 Agent 运行时**不承担权限判定职责**，把鉴权下沉到"Agent 网关 + 独立授权引擎"，运行时只负责推理与编排。

**判断五：流程节点上的护栏必须是结构化的，不能是提示词式的。** 提示词里的"删除前必须审批"只是建议；建模为必须经过人工审批的流程子过程才是强制——Agent 无论怎么推理都绕不过去。

> 以上五条判断的业界依据（Entra Agent ID、Agentforce、Glean、M365 Copilot 治理蓝图、Zanzibar/OpenFGA、Camunda、MCP 授权规范、ID-JAG、OWASP）见 `agent-platform-insight-0001`。

## 1. 平台总体架构

```
┌──────────────────────────────────────────────────────────────────────────┐
│  L6 治理面（贯穿全栈）                                                     │
│  审计中心 │ 数字员工台账 │ 访问评审 │ 评测与红队 │ 成本与配额 │ 密级与DLP    │
└──────────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────┐
│  L1 接入层                                                                │
│  IM对话(企微/钉钉/飞书) │ Web工作台 │ 流程节点触发 │ OpenAPI │ IDE/工具侧   │
└───────────────┬──────────────────────────────────────────────────────────┘
                │  携带：用户身份令牌 + 场景标识
┌───────────────▼──────────────────────────────────────────────────────────┐
│  L2 编排层：业务流程引擎（BPMN）                                           │

│  L3 数字员工运行时                                                        │
│  会话管理 │ 规划与推理 │ Skill装配 │ 记忆管理 │ 无状态执行体（容器/沙箱）    │

└───────────────┬──────────────────────────────────────────────────────────┘
                │  所有对外调用一律出网关，无直连
┌───────────────▼──────────────────────────────────────────────────────────┐
│  L4 能力供给层：Agent 网关（MCP / A2A / LLM 统一出口）                      │
│  工具注册与联邦 │ 策略决策点(PDP) │ 令牌交换 │ 限流与预算 │ 全量调用留痕      │
└───────┬───────────────────────────────┬──────────────────────────────────┘
        │                               │
┌───────▼──────────────────┐  ┌─────────▼────────────────────────────────┐
│  L5A 知识层（权限感知RAG） │  │  L5B 系统层（业务系统 MCP Server）        │
│  ACL镜像索引 │ 向量库分区   │  │  PLM/PDM │ 需求/缺陷 │ 代码库 │ 表格系统  │
│  检索时鉴权 │ 引用溯源      │  │  一律以"用户身份"访问，禁用超级账号        │
└──────────────────────────┘  └──────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────────┐
│  L0 身份与信任层                                                          │
│  企业IdP │ 数字员工身份(Agent Principal) │ 责任人绑定 │ 授权引擎(FGA) │ 审计 │
└──────────────────────────────────────────────────────────────────────────┘
```

**架构上的四条铁律【设计】**

1. **无直连**：运行时不得直接访问任何数据源或外部 API，全部经 L4 网关。这样策略决策点只有一个，审计口径也只有一个。
2. **无超级账号**：任何组件不得使用具备全局读权限的服务账号去读业务数据。数字员工自身不携带数据权限。
3. **权限判定不下放给模型**：模型不参与"能不能看"的判断，只参与"看到之后怎么办"。
4. **流程引擎是状态真相源**：Agent 保持无状态或短状态，便于重放、审计和故障恢复。

## 2. 数字员工的身份与授权模型（核心设计）

### 2.1 身份三元组【设计，参照 Entra Agent ID 的 agent identity + sponsor + OBO 结构】

每一次数字员工的动作，都必须能回答三个问题：

| 维度 | 含义 | 承载物 |
|---|---|---|
| **Agent Principal** | 这是哪个数字员工 | IdP 中的独立身份，有唯一 ID、凭据、生命周期 |
| **Sponsor / Owner** | 出事找谁 | 责任人（个人 + 归属部门），随身份生命周期强制存在 |
| **Acting-For** | 此刻代表谁在做事 | 会话中的委派主体（发起用户 / 流程实例 / 岗位） |

审计日志的每一条记录必须同时含这三项，缺一不可。

### 2.2 有效权限公式【设计】

```
有效权限 = P(数字员工职权) ∩ P(委派主体) ∩ P(当前任务作用域)
```

三重交集取最小。三者的来源分别是：

- **P(数字员工职权)**：由岗位模板定义，比如"接口评审专家"只能读接口规格类文档、只能写评审意见，永远不能读薪酬、不能删除任何东西。
- **P(委派主体)**：代客模式下就是发起用户在源系统的真实权限；职务模式下是流程节点绑定的岗位权限。
- **P(当前任务作用域)**：由本次任务的对象范围限定，比如"图纸 D-1024 的接口评审"只授予该图纸及其关联规格的读权限，任务结束即失效。

第三项是 Agentforce 那类"纯继承用户权限"模型缺失的一层，也是防止"数字员工顺手把用户全部历史权限暴露出来"的关键。

### 2.3 两种运行模式【设计】

| | **代客模式（On-Behalf-Of）** | **职务模式（Role-Based）** |
|---|---|---|
| 典型场景 | 员工在对话框里问问题 | 流程节点自动触发的评审 |
| 权限来源 | 发起用户的真实权限 | 流程节点绑定的岗位权限 |
| 能看到什么 | 只能是用户本来就能看到的 | 只能是该评审岗位本来就能看到的 |
| 输出可见性 | 只对该用户可见 | 写入流程实例，按流程可见性规则 |
| 典型风险 | 放大用户的历史过度权限 | 岗位权限被当成万能钥匙 |
| 对应控制 | 叠加任务作用域裁剪 | 岗位权限按评审类型细分，禁止合并成"评审专家"一个大角色 |

**关键约束**：职务模式下产出的内容，回流到代客模式对话时必须重新做一次可见性判定。不能因为"数字员工在流程里看过"就允许它在聊天里讲出来。这是最容易被忽略的泄漏路径。

### 2.4 令牌链设计【业界规范约束 + 设计】

严格遵循 MCP 授权规范的硬要求：

```
用户 --SSO--> IdP
  │
  └─> 运行时持有：用户身份断言（ID Token / SAML Assertion）
        │
        └─ 令牌交换（RFC 8693 / ID-JAG）在 IdP 完成，由企业策略决定放不放行
              │
              └─> 网关获得：面向【特定下游资源】受众的短时效访问令牌
                    │  必须携带 resource 参数（RFC 8707）
                    │  必须包含 act 声明（谁在代表谁行动）
                    └─> 下游 MCP Server 校验 aud，拒绝非本服务令牌
```

绝对禁止的三件事：

1. 把用户传进来的令牌原样转发给下游（令牌透传）。
2. 用一个长期有效、宽作用域的 API Key 代替上述链路。
3. 在工具调用参数里传令牌（规范已明确令牌只走 HTTP 头）。

令牌时效建议（初始值，待压测校准）：会话级 ≤ 15 分钟，任务级 ≤ 单次任务预估时长 × 2，且不可续期超过 3 次。

### 2.5 数字员工的"人事"生命周期【设计，对标 Entra ID Governance 的做法】

| 环节 | 动作 | 强制项 |
|---|---|---|
| 入职 | 在 IdP 注册身份、绑定责任人、登记岗位模板 | 无责任人不得创建 |
| 授权 | 通过权限包申请数据域与工具集 | 走与人相同的审批流 |
| 试用 | 影子模式运行（只产出建议，不生效） | 通过评测集才能转正 |
| 在岗 | 按自治度分级运行 | 每次动作全量留痕 |
| 定期评审 | 季度访问评审，未使用的权限自动回收 | 责任人须签字确认 |
| 转岗 | 变更岗位模板，旧权限即时失效 | 不允许权限累加 |
| 离职 | 凭据吊销、身份停用、历史留档 | 关联的流程节点须先改派 |

**"未使用即回收"这条必须自动化**——Entra 团队指出的核心风险正是"运行时获得权限、随时间累积、无限期保留"。

## 3. 数据隔离与权限管控（重点）

### 3.1 七道闸门总览【设计，综合 Glean / Copilot 蓝图 / OpenFGA / OWASP】

```
G1 源端治理  →  G2 摄取隔离  →  G3 存储隔离  →  G4 检索隔离
                                                    ↓
        G7 输出与审计  ←  G6 动作隔离  ←  G5 会话与记忆隔离
```

任何一道单独都不足以防住"用户问到他人数据"，必须叠加。

### G1 源端治理（上线前置，不可跳过）

对标微软 Copilot 蓝图的 Pilot → Deploy → Operate。**这一步做不完，平台就不该开放给普通用户。**

| 动作 | 说明 |
|---|---|
| 过度共享扫描 | 盘点各业务系统中"全员可见""任何人可见""继承断裂""无属主"的内容 |
| 密级标注 | 至少三级（公开/内部/受限），受限内容默认不进索引 |
| 不入库清单 | 薪酬、绩效、人事、法务、并购、个人信息等整域排除，宁可牺牲能力 |
| 临时遏制 | 整改未完成的高风险数据域，先用"索引可见性开关"整体屏蔽（对标 RCD），不改动源权限 |
| 源端整改 | 修权限、补属主、访问评审 |
| 常态化 | 新建空间默认最小可见、关闭全员共享组、周期性复扫 |

**关键设计点**：把"检索可见性"和"访问权限"做成两个正交开关。RCD 的经验说明，有些内容需要保持可访问但不该被广泛发现——这是数字员工场景特有的需求。

### G2 摄取隔离（ACL 与内容同步入库）

对标 Glean 的 ACL 镜像做法：

- 每个 chunk 强制携带元数据：`tenant_id` / `space_id` / `source_system` / `source_doc_id` / `acl_ref` / `classification` / `acl_version` / `ingested_at`。
- **ACL 不内联展开成用户列表**，只存引用（指向授权引擎中的对象），避免"元数据爆炸"和权限变更时的全量重建。
- 增量同步：源系统权限变更通过 webhook 或定期 diff 回流，记录同步延迟指标。
- **降密/删除的补偿机制**：源文档被删除或收紧权限时，必须有确定性的索引失效路径，且失效延迟要有 SLA 与告警。这是最容易出事的地方——ACL 同步延迟就是泄漏窗口。
- 自定义数据源接入时，必须先索引用户与组关系，才能引用其权限（Glean 索引 API 的强制要求，同样适用于自建）。

### G3 存储隔离（分级隔离策略）

Milvus 官方支持四个级别的多租户，各有取舍：

| 级别 | 隔离强度 | 规模上限 | 适用 |
|---|---|---|---|
| Database 级 | 完全隔离，适合强合规 | 默认最多 64 个 | 密级最高的少数域 |
| Collection 级 | 较强 | 中等 | 部门级/大业务域 |
| Partition 级 | 中 | 中等 | 项目级 |
| Partition Key 级 | 逻辑隔离，扩展性最好 | 高 | 用户级/团队级，但不支持批量导入 |

**【设计】建议的三档策略**：

- **受限域**（人事、法务、财务、核心 IP）→ 独立实例或独立 Database，物理隔离，独立密钥，独立审计流。
- **业务域**（各研发领域）→ Collection 级隔离，一个领域一个 collection。
- **域内细分**（项目/团队/个人）→ Partition Key，配合检索时的强制过滤条件。

关系型元数据侧建议叠加 PostgreSQL 行级安全（RLS），做兜底——即使应用层漏写了过滤条件，数据库层也拦得住。

### G4 检索隔离（预过滤 vs 后过滤）

这是性能与安全的核心权衡点。Descope 的分析指出预过滤在向量库里会遇到三个问题：权限同步滞后、元数据爆炸、复杂权限下的性能开销；因此主张后置过滤 + 迭代重查询补齐。

**【设计】建议采用混合三段式**：

```
第一段：硬边界预过滤（必须）
  在向量检索的 filter 表达式里强制注入 tenant_id / space_id / classification 上限
  → 这些是低基数、变更极少的粗粒度边界，预过滤代价小、收益大
  → 且能防住"跨租户/跨密级"这类最严重的越权

第二段：语义检索（放大 top-k）
  实际取 K' = K × α（α 建议 3~5，按历史过滤率动态调整）

第三段：细粒度后过滤（必须）
  逐 chunk 调用授权引擎批量 Check（ReBAC），过滤掉无关系的
  不足 K 条时，分页迭代重查询补齐，最多 N 轮（建议 N=3）
  N 轮后仍不足则如实返回并告知"可用资料有限"
```

**为什么两头都要**：只做预过滤，细粒度权限（个人授权、临时授权、关系传递）表达不了；只做后过滤，跨租户数据会进入检索管道，一旦后过滤逻辑有 bug 就是灾难性泄漏。粗边界预过滤 + 细粒度后过滤是纵深防御。

**授权引擎选型**：OpenFGA（CNCF、Zanzibar 模型、ReBAC 可表达 RBAC 与 ABAC）。注意其已知局限——Zanzibar 系模型是为人类主体设计的，多 Agent 委派链需要自行建模（建议把 Agent 也建为主体类型，把委派建为关系）。

**性能兜底**：授权引擎必须支持批量 Check 与本地缓存（带 TTL 和主动失效），否则 top-50 的逐条鉴权会成为延迟瓶颈。

### G5 会话与记忆隔离

OWASP 明确把"记忆投毒"列为关键风险：恶意数据被持久化进记忆后，会影响后续会话**或其他用户**。相关研究还指出记忆泄漏问题——持久化对话记忆本身就是隐私攻击面。

**【设计】记忆分域模型**：

| 记忆类型 | 作用域 | 可见性 | 写入权限 |
|---|---|---|---|
| 会话记忆 | 单会话 | 仅本会话 | 系统 |
| 用户记忆 | 用户 × 数字员工 | 仅该用户 | 用户显式确认 |
| 岗位知识 | 数字员工岗位 | 该岗位全部实例 | 需人工评审后入库 |
| 组织知识 | 空间/租户 | 按 ACL | 走 G1~G2 的正规入库流程 |

强制规则：

- **上一层不得读下一层**：岗位知识里绝不允许出现从用户会话中"学"到的具体业务数据。这是跨用户泄漏最隐蔽的一条路径。
- 记忆写入必须记录来源（provenance），并对新增记忆做敏感内容扫描。
- 只允许可信、已认证来源写入记忆；限制保留期。
- 定期做记忆审计：抽样检查是否存在应属于用户 A 的内容出现在跨用户可见层。

### G6 工具与动作隔离

在 Agent 网关（推荐 agentgateway，Apache 2.0，Linux Foundation 项目）上落地：

- **工具白名单**：每个数字员工岗位对应一份工具清单，网关侧强制，运行时无法自行扩展。
- **策略语言**：agentgateway 内置基于 Cedar 的细粒度授权，可同时表达 RBAC / ABAC / ReBAC，策略声明式、可审计、与代码分离。例如允许某角色调用 `crm_search` 但禁止 `crm_delete`。
- **参数级约束**：不只管"能不能调这个工具"，还要管"参数落在什么范围"。比如查询类工具的 `owner` 参数必须等于当前委派主体。
- **读写分离**：默认只授予读工具；写工具单独申请，且必须在 BPMN 里有对应的审批节点。
- **高影响动作**：要求动作级二次确认与 dry-run 预演（OWASP 建议）。
- **防工具投毒**：网关侧校验 MCP Server 的工具描述变更，描述变更视为需要重新评审的配置变更。
- **预算与限流**：按数字员工、按岗位设 token 与调用配额，防"钱包拒绝服务"。

### G7 输出与审计

- **出参检查**：结构化输出 + 密级校验，凡引用的 chunk 密级高于当前会话上限则拦截。
- **引用强制**：所有事实性断言必须携带可点击的溯源链接，用户点不进去的链接就是泄漏信号——这同时也是一个天然的越权自检机制。
- **"为什么我能看到这条"**：审计台支持对任一条返回内容反查其授权路径。
- **越权探测告警**：对"检索命中但被过滤"的比例做监控。某用户短时间内大量触发过滤，是探测行为的信号。
- **审计三元组**：每条日志含 Agent Principal + Sponsor + Acting-For + 工具 + 参数摘要 + 命中文档 ID 列表 + 决策依据。
- 追踪与日志本身也要脱敏——可观测系统是被忽视的泄漏面。

### 3.2 "用户问到他人数据"的六条典型泄漏路径与对策【设计】

| # | 泄漏路径 | 为什么容易发生 | 对策 |
|---|---|---|---|
| 1 | 索引时丢了 ACL | 自建 RAG 常常只存内容不存权限 | G2 强制元数据 Schema，缺 acl_ref 的 chunk 拒绝入库 |
| 2 | 权限变更未同步 | 源系统收紧权限，索引仍是旧的 | G2 增量回流 + 同步延迟 SLA + 高密级内容改为查询时实时校验 |
| 3 | 跨用户共享记忆/缓存 | 为了省 token 或提速，把摘要缓存成公共资产 | G5 记忆分域铁律；缓存 Key 必须含委派主体 |
| 4 | 多 Agent 转交丢身份 | A2A 交接时下游 Agent 用了自己的权限 | 委派链必须逐跳传递并收窄，禁止"扩权交接"；Zanzibar 模型不原生支持这点，需自行建模 |
| 5 | 工具用服务账号 | 集成图省事，MCP Server 用了管理员凭据 | 无超级账号铁律；接入评审时检查凭据类型；令牌必须带 act 声明 |
| 6 | 职务模式内容回流对话 | 数字员工在流程里看过的东西，在聊天里说了出来 | 2.3 的关键约束：跨模式必须重新判定可见性 |

**红队用例应当逐条覆盖这六项，并纳入回归测试**（OWASP 建议把已发现的注入、记忆投毒、工具滥用失败模式做成回归测试，并在工具策略、审批逻辑、凭据作用域变更时阻断发布）。

## 4. 数字员工嵌入流程节点（评审场景）

### 4.1 节点类型与建模【设计，对标 Camunda 的职责切分】

在 BPMN 里区分三类节点：

| 节点类型 | 语义 | 建模方式 |
|---|---|---|
| 人工节点 | 人做，AI 不介入 | User Task |
| AI 辅助节点 | AI 出建议，人决策 | User Task + 附加的 AI 建议（虚线关联数字员工） |
| AI 自主节点 | AI 在护栏内自行完成 | Service Task / Ad-hoc Sub-process（实线由流程箭头指向数字员工） |

职责边界照搬 Camunda：**LLM 决定调什么工具、什么顺序、什么参数；流程引擎负责执行、存状态、重试、异常和人工任务路由。** Agent 可用的每个工具都是流程里的一个活动，构成"受治理的工具箱"。

### 4.2 评审数字员工的任务契约【设计】

每个评审节点必须定义一份契约，作为数字员工与流程之间的接口：

```yaml
task_contract:
  节点: 接口评审
  数字员工岗位: interface-review-expert
  运行模式: 职务模式
  输入:
    - 交付件: 图纸/接口规格文档（只读）
    - 依据: 接口设计规范 v3.2、历史评审知识库（限本领域）
    - 上下文: 变更点 diff、关联需求
  权限作用域:
    数据域: [interface-specs, drawings/{doc_id}, review-history/interface]
    工具: [doc_read, spec_search, review_comment_write]
    禁止: [任何删除、任何跨领域读取、任何人事/财务域]
  输出Schema:
    items:
      - 条目ID / 问题描述 / 严重度(阻塞|主要|次要|建议)
      - 违反的规范条款（必须可溯源引用）
      - 证据位置（文档+页码/坐标）
      - 置信度
    结论: 通过 | 有条件通过 | 不通过 | 无法判定
  责任边界:
    自动通过: 仅当 无阻塞项 且 无主要项 且 全部条目置信度 ≥ 阈值
    强制转人工: 存在阻塞项 / 置信度低于阈值 / 输出"无法判定" / 首次评审该类交付件
  失败处理:
    最大规划循环: 8
    超时: 15 分钟
    失败即返回结构化"无法完成"+原因，升级为人工任务
```

**"无法判定"必须是一等输出**，而不是被逼着给一个结论。Camunda 的经验是把失败设为一等结果：达到重试上限后返回结构化的"无法完成"及原因与上下文，并按流程模型升级——这样失败可观测、可审计、成本可控。

### 4.3 自治度演进路线【设计，对标 Camunda 的渐进式主张】

| 阶段 | 模式 | 特征 | 转阶段条件 |
|---|---|---|---|
| L1 影子 | AI 跑但结果不进流程 | 与人工评审结果对比 | 一致率达标 |
| L2 建议 | AI 出意见，人必看必签 | 人的工作从"从头看"变成"审 AI 的意见" | 意见采纳率、漏检率达标 |
| L3 分级自主 | 低风险类别自动通过，其余转人工 | 阈值可调、可回滚 | 自动通过区间零重大逃逸 |
| L4 主责 | AI 主责，人抽检与兜底 | 人的角色转为质量抽样与规则维护 | —— |

注意这不是一次性设计决策，而是一段旅程：先让 Agent 只做建议、人始终在环，随着模式稳定再逐步调高自治度——先自动通过低风险案例，再扩大阈值，再扩展类别。

**每一次自治度提升都必须是一次有审批的配置变更，且可一键回滚。**

### 4.4 评审结果的可审查性【设计】

- 每条评审意见可回溯到：依据的规范条款 + 证据位置 + 使用的模型版本 + 提示词版本 + 工具调用轨迹。
- 保留证据以支持事后复核（OWASP 建议保留：测试过的 Agent 版本、模型提供方、工具策略、检索配置）。
- 提供"申诉"通道：被评审方可对某条意见提出异议，异议样本自动进入评测集——这是让数字员工进化的燃料。

## 5. 开源选型建议

### 5.1 分层选型表【业界事实 + 设计建议】

| 层 | 首选 | 备选 | 关键事实与提示 |
|---|---|---|---|
| 流程引擎 | **Flowable Community**（Apache 2.0） | Activiti、Temporal | Camunda 8 的 Zeebe/Operate/Tasklist 采用 Camunda License 1.0，属**源码可得而非开源**，其社区许可限制"允许终端用户修改或部署流程模型的托管服务"；Camunda 7 已在退役。若只做内部平台通常可控，但需法务确认。**Camunda 的 agentic orchestration 设计思想值得全盘借鉴，选型可另议。** |
| Agent 运行时 | **Coze Studio**（Apache 2.0，2025-07 由字节开源，Go + TS） | Dify、LangGraph、自研 harness | **Dify 社区版官方文档明确不支持开通多个工作空间**，多租户与 SSO/RBAC 属企业版能力；社区普遍反馈开源版原生企业级权限、审计能力薄弱，政企场景需大量二次开发。**因此不要把权限判定交给运行时。** |
| Agent 网关 | **agentgateway**（Apache 2.0，Linux Foundation） | Envoy/Higress 自建 | Rust 实现；统一 LLM / MCP / A2A / HTTP 四种模式；内置 JWT 认证与 RBAC，基于 Cedar 做工具级策略；MCP 授权规范合规（对接 Keycloak、Auth0）；内置 OpenTelemetry 指标与追踪；支持 MCP 工具联邦（多后端聚合成单一目录）；支持多租户 |
| 授权引擎 | **OpenFGA**（CNCF，Okta 维护） | SpiceDB、Cedar 单用 | Zanzibar 模型的开源实现；策略 DSL 本身即策略文件，可入 Git、走 PR 评审、像代码一样发布 |
| 身份 | **Keycloak** | 企业既有 IdP | 需支持 RFC 8693 令牌交换；ID-JAG 已有跨 Okta/Keycloak 的互操作实践 |
| 向量库 | **Milvus** | pgvector + RLS | 四级多租户，Database 级最多 64 租户；Partition Key 级扩展性最好但不支持批量导入 |
| 元数据库 | PostgreSQL + RLS | —— | 行级安全作为应用层过滤的兜底 |
| 可观测 | **Langfuse** / **CozeLoop**（Apache 2.0） | OTel GenAI 语义约定自建 | CozeLoop 与 Coze Studio 同期开源，覆盖调试追踪 |
| 评测红队 | **promptfoo** | 自建评测集 | 已内置 OWASP Agentic 风险的红队用例集 |

### 5.2 选型的三条原则【设计】

1. **鉴权组件与运行时解耦**。运行时可以换（Dify → Coze Studio → 自研），网关与授权引擎不能换来换去——它们是安全边界，也是审计口径的来源。
2. **优先选 Apache 2.0**。Camunda License、SSPL、Elastic License 这类源码可得许可证在企业内部通常可用，但若未来平台要作为服务对外提供（哪怕只是集团内跨法人），必须先过法务。
3. **不要为了"一个平台搞定"而牺牲隔离**。低代码 Agent 平台的卖点是快，但它的权限模型往往是为"一个团队一个工作空间"设计的，不是为"上千个数字员工、上万名员工、多密级数据"设计的。

## 6. 关键流程时序

### 6.1 员工对话查询（代客模式）

```
1. 员工在 IM 中 @ 数字员工提问
2. 接入层校验用户 SSO 身份，生成会话，绑定 Acting-For = 该用户
3. 运行时组装上下文（岗位提示词 + 会话记忆 + 用户记忆），不含任何业务数据
4. 运行时经网关发起检索：
   4.1 网关校验：该数字员工是否被授权使用 knowledge_search 工具（Cedar 策略）
   4.2 网关在 IdP 完成令牌交换，取得面向知识服务、含 act 声明的短时效令牌
   4.3 知识服务预过滤（tenant/space/密级上限）→ 语义检索 top-K'
   4.4 逐 chunk 调授权引擎批量 Check（主体 = 用户，非数字员工）
   4.5 不足 K 条则分页补齐，最多 3 轮
5. 运行时用过滤后的 chunk 生成回答，强制附引用
6. 出参检查：密级校验 + DLP + 引用可达性
7. 审计：记录 Agent Principal / Sponsor / Acting-For / 命中文档 ID / 过滤条数
8. 返回员工
```

第 4.4 步的主体是**用户而非数字员工**——这是代客模式的本质。

### 6.2 流程节点触发评审（职务模式）

```
1. 图纸提交，流程引擎推进到"接口评审"节点
2. 流程引擎创建任务实例，下发任务契约（4.2），Acting-For = 流程实例 + 岗位
3. 运行时拉起数字员工实例（无状态容器），注入契约与作用域
4. 运行时经网关读取交付件与规范：作用域被限制在契约声明的数据域内
   ★ 不使用发起人的权限，使用岗位权限 ∩ 任务作用域
5. 生成结构化评审意见（含条目、严重度、规范条款引用、证据位置、置信度）
6. 按责任边界判定：
   - 全部条件满足 → 自动通过，写回流程变量
   - 否则 → 创建人工任务，把 AI 意见作为附件呈现给主审人
7. 主审人签署（或修改）意见，流程继续
8. 意见与人工修正的 diff 自动入评测集
9. 审计留痕：模型版本 + 提示词版本 + 工具调用轨迹 + 引用清单
```

### 6.3 数字员工发起写操作

```
1. 运行时提出写操作意图（如"在缺陷系统创建一条记录"）
2. 网关策略判定：该岗位是否持有该写工具？参数是否在允许范围？
3. 若为高影响动作 → 先 dry-run，把预演结果交给 BPMN 的审批节点
4. 人工审批通过 → 网关换取写作用域令牌 → 执行
5. 执行结果与审批记录一并写入流程实例
```

**审批节点建模在 BPMN 里，而不是写在提示词里**——这是不可绕过与可绕过的区别。

## 7. 落地路线图

| 阶段 | 目标 | 关键交付 | 准入 / 退出条件 |
|---|---|---|---|
| **阶段 0：治理前置**（建议 2~3 个月，与平台开发并行但独立验收） | 把数据权限债务摸清并遏制 | 过度共享扫描报告、密级标注规范、不入库清单、索引可见性开关 | 退出：高风险数据域 100% 完成"遏制或整改"；无遗留的全员可见敏感空间 |
| **阶段 1：安全底座** | 身份、网关、授权引擎跑通 | IdP 中的数字员工身份体系、agentgateway + Cedar 策略、OpenFGA 模型、审计中心 | 退出：红队六条泄漏路径全部有对应用例且通过 |
| **阶段 2：单场景闭环** | 一个评审场景 L1→L2 | 权限感知 RAG、一个评审数字员工、BPMN 节点接入、评测集 | 准入：阶段 1 通过；退出：影子模式一致率与漏检率达标 |
| **阶段 3：横向复制** | 数字员工岗位模板化 | 岗位模板机制、数字员工市场、自助创建与审批流 | 退出：新增一个岗位的边际成本可量化 |
| **阶段 4：自治度提升** | 部分节点 L3 | 阈值机制、自动通过区间、抽检机制、申诉通道 | 退出：自动通过区间内零重大逃逸，连续 N 个周期 |

**阶段 0 不能跳过。** 这是微软蓝图给出的最重要经验：先治理数据，再上线 AI。跳过它的后果是上线首周就出现"某某问出了他不该看到的东西"，然后整个项目被叫停。

## 8. 度量指标

### 安全类（一票否决）

- 越权命中率：红队用例中成功获取越权数据的比例（目标 0）
- ACL 同步延迟 P95 / P99（目标：受限域实时校验，其余 < 5 分钟）
- 缺失 `acl_ref` 的 chunk 数量（目标 0）
- 审计三元组完整率（目标 100%）
- "检索命中但被过滤"的异常用户告警响应时长

### 效能类

- 评审节点周期时间（对比接入前）
- AI 评审意见采纳率
- 人工复核率与复核耗时
- 漏检率（AI 通过但人工发现问题的比例）——这是最关键的质量指标
- 误报率（AI 报出但被人工驳回的比例）

### 运营类

- 在岗数字员工数量、活跃度、闲置率
- 单次任务成本（token + 工具调用）
- 岗位模板复用率
- 权限回收率（季度评审中被自动回收的权限占比）

## 9. 风险与开放问题

| 风险 | 说明 | 缓解 |
|---|---|---|
| **提示注入仍无根本解** | 论文作者的诚实结论：只要 Agent 与其防御都依赖当前这代模型，通用型 Agent 就难以提供可靠的安全保证 | 用架构收窄能力边界：评审类数字员工采用 Plan-Then-Execute 或 Map-Reduce 模式，处理不可信文档的环节不给工具权限 |
| **多 Agent 委派链的授权** | Zanzibar 系模型为人类主体设计，不原生支持 Agent 委派链 | 把 Agent 建为主体类型、委派建为关系；A2A 交接强制权限收窄，禁止扩权 |
| **ACL 同步延迟即泄漏窗口** | 增量同步必然有延迟 | 受限域改为查询时实时回源校验，牺牲延迟换安全 |
| **开源许可证风险** | Camunda License 1.0 等源码可得许可证对"托管服务"有限制 | 选型前过法务；优先 Apache 2.0 |
| **开源 Agent 平台的企业级能力缺口** | Dify 社区版不支持多工作空间；开源平台的权限审计能力普遍偏弱 | 权限判定下沉到网关与授权引擎，运行时可替换 |
| **影子 Agent** | 业务侧绕过平台自建 Agent（Agentforce 的真实教训） | 数字员工台账 + IdP 侧身份发现 + 网关是唯一出口（无网关则无法调用模型与工具） |
| **过度信任** | OWASP 列出的风险之一：用户过度信任 Agent 的建议 | 强制引用、置信度显示、"无法判定"作为一等输出、保留人工兜底 |

### 归档时补充的开放问题（尚未在原方案中回答）

| # | 问题 | 阻塞什么 | 建议决策方式 |
|---|---|---|---|
| 1 | 目标企业现有 IdP 是否支持 RFC 8693 令牌交换？不支持时是引入 Keycloak 做联邦，还是降级方案？ | 令牌链（2.4）整体成立与否 | 阶段 1 前做 IdP 能力摸底 |
| 2 | Flowable 是否具备 Camunda 那样的 ad-hoc 子流程 / AI 任务节点原语？若无，L2 编排层的设计需要多少自研？ | 选型表首选项与阶段 2 工作量 | PoC 验证，不能只看许可证选型 |
| 3 | 受限域"查询时实时回源校验"的延迟预算是多少？用户可接受的对话响应上限？ | G4 与 3.2#2 的对策可行性 | 压测 + 用户体验基线 |
| 4 | 岗位模板的粒度由谁定义、谁审批？安全团队还是业务团队？ | 阶段 3 的组织落地 | 需要明确 RACI |
| 5 | 评测集与红队用例由谁维护？漏检率的达标线定在多少？ | L1→L2→L3 的转阶段判据 | 与质量部门共同定义 |
