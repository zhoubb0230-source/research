# Agent-Ready 仓库与工作流落地方案：从可验证边界到分层上下文

> 业界依据见 `ai-coding-insight-0002`。本方案只解决「我们的仓库和工作流该怎么改」，不涉及工具采购与人员组织调整。

## TL;DR

- **目标**：把仓库从「Agent 读的文本」改造成「Agent 的运行时」，使 Agent 的产出可被自动判定，人从验证回路中退出来。
- **推荐方案**：三级递进的 **L1 可验证边界 → L2 分层上下文 → L3 选择性规格驱动**。**顺序不可颠倒**，L1 未达标的仓库不进入 L2/L3。
- **关键取舍**：明确**不**先引入 Spec Kit 类重型 SDD 工具链。理由是其收益对小任务为负、对模型进步敏感、且强依赖具体工具；而 L1/L2 收益确定、成本低、不依赖工具选型。
- **预估投入 / 周期**：单仓库 L1 约 3–5 人日、L2 约 2–3 人日；P0 验证 2 周（2 个试点仓库），P1 试点 6 周（5–8 个仓库），P2 推广按仓库自助化。

## 1. 背景与目标

### 1.1 问题陈述

当前 AI Coding 的使用形态是「人提要求 → Agent 改代码 → **人逐行审查**」。这个链路有三处结构性损耗：

1. **人是验证回路本身。** Agent 在「看起来完成」时停止，没有它能自己跑的检查时，每一个错误都要等人发现。这使 Agent 的产能上限被人的审查带宽锁死。
2. **约束不被遵守，且模型进步救不了。** 20,574 个真实会话的研究显示，90.50% 的失配只造成努力与信任成本而非系统损害，但 **91.49% 的可见修复仍需用户显式纠正**；且随模型进步，「违反约束」与「不实自述」两类失配的**占比在上升**。这两类恰恰是建议性质的上下文文件解决不了的。
3. **上下文文件只增不减。** 业界普遍停留在「写一个 AGENTS.md」（2,853 仓库实证：Context Files 常是唯一被采用的机制），而文件越长遵从度越低是已被明确警示的失效模式。

> 数据来源与可靠性标注见 `ai-coding-insight-0002` §0 与参考资料。

### 1.2 目标与非目标

| | 内容 |
|---|---|
| **目标** | ① 每个纳管仓库具备 Agent 可自主运行的 pass/fail 检查，并在上下文文件首屏声明；② 测试与契约成为 Agent 不可篡改的资产；③ 上下文指令按作用域分层，根文件受行数约束且有淘汰机制；④ 建立可度量的「Agent 就绪度」，用于决定推广顺序 |
| **非目标** | ① 不做工具选型与采购决策（本方案对 Claude Code / Cursor / Codex 均适用）；② 不改变团队角色分工与考核方式；③ 不引入重型 SDD 工具链（见 §3 选型）；④ 不做研发效能度量体系建设（另立专题） |

### 1.3 成功指标

| 指标 | 现状 | 目标（P1 结束时） | 度量方式 |
|---|---|---|---|
| 仓库 Agent 就绪度评分（见 §4.2） | 未度量 | 试点仓库 ≥ 0.6 | 自动化脚本每周扫描 |
| Agent 产出的 PR 中「无需人工修正即通过全部门禁」的比例 | 未度量 | ≥ 50% | CI 首次运行结果统计 |
| Agent PR 合并冲突率 | 未度量 | ≤ 20%（业界参考 27.67%） | PR 元数据统计 |
| 测试弱化/删除的拦截次数与绕过次数 | 无拦截机制 | 绕过次数 = 0 | hook 日志 |
| 根上下文文件行数 | 未约束 | 100% 仓库 ≤ 200 行 | 扫描脚本 |
| 过期上下文规则清理率 | 无机制 | 每模型大版本后完成一轮重审 | 评审记录 |

## 2. 约束与前提

**技术约束**
- 各仓库技术栈不统一，方案必须以「能力要求」而非「具体工具」表述，检查命令由各仓库自行实现。
- 部分遗留仓库无可运行测试套件，L1 对其成本远高于均值，需单独排期。

**方案成立所依赖的假设**
- **假设 A（强）**：仓库清洁度是 AI 收益的前置条件而非结果。依据为 27 团队样本 R²≈0.40、清洁度 <0.3 常见负收益的研究结论。**该结论来自二手转述，尚未复核原文**——若被证伪，P2 阶段的「按就绪度排推广顺序」策略需要重排，但 L1/L2 的投入本身仍然成立（其收益由验证回路与上下文遵从度直接支撑，不依赖此假设）。
- **假设 B**：所选 Agent 工具支持生命周期 hook（工具调用前拦截、回合结束门禁）。Claude Code 已确认支持；Cursor / Codex 需在 P0 实测（列入 §8 开放问题）。
- **假设 C**：模型能力持续提升，但「遵守约束」与「如实自述」不会随之自动解决。这是把投入压在硬边界而非提示词上的核心理由。

## 3. 方案选型

| 候选方案 | 优势 | 劣势 | 成本 | 风险 | 结论 |
|---|---|---|---|---|---|
| **A. 三级递进（可验证边界 → 分层上下文 → 选择性 SDD）** | 收益顺序与确定性一致；不依赖工具选型；每级可独立止损 | 见效慢于「装个工具」；需要仓库侧真实投入 | 中 | 低 | **推荐** |
| B. 引入 Spec Kit / Kiro 类重型 SDD 工具链 | 流程完整、有现成模板与阶段门禁；对外可讲的故事完整 | 小任务净负债（实测 33min + 2,577 行 markdown → 689 行代码，对照迭代式 8min）；规格-代码同步税；强工具绑定；对模型进步敏感 | 高 | 中高 | **否决为默认路径**，保留为 L3 的可选试点 |
| C. 只做上下文文件（写好 AGENTS.md 就完事） | 成本极低，一周可铺开 | 不解决约束违反与不实自述；文件膨胀后遵从度反降；等于把验证成本继续压在人身上 | 极低 | 高（虚假完成感） | 否决 |
| D. 只做工具侧治理（权限白名单、审批流） | 安全侧收益直接 | 审批疲劳会让审查退化为点击；不产生任何正向产能 | 低 | 中 | 否决为独立方案，其内容并入 L1 的执行边界 |

**选型理由**：把候选按「确定收益 ÷ 落地成本 × 抗模型进步性」排序，验证驱动与分层上下文明显优于规格驱动，而这与业界声量的排序几乎相反。方案 A 的本质是**按证据强度而非声量决定投入顺序**。

**切换条件**：若 P1 试点中出现「跨团队协作的大型需求，因意图对齐失败导致返工超过 2 次」的重复案例，则在该类项目上启用 L3 的重型 SDD 试点（方案 B），限定范围而非全面铺开。

## 4. 架构设计

### 4.1 总体架构：仓库作为 Agent 运行时的四个面

```
                    ┌─────────────────────────────────────┐
                    │           Agent 会话                 │
                    └──────┬───────────────────────┬──────┘
                           │ 读                    │ 写/执行
              ┌────────────▼──────────┐   ┌────────▼─────────────┐
              │  ② 上下文面（L2）      │   │  ③ 执行面（L1）       │
              │  分层指令 / 作用域规则  │   │  沙箱边界             │
              │  按需知识 / 领域事实    │   │  文件系统 + 网络白名单 │
              └───────────────────────┘   └────────┬─────────────┘
                                                   │ 产出 diff
              ┌────────────────────────────────────▼─────────────┐
              │  ① 验证面（L1）—— 本方案的地基                     │
              │  类型 · 契约 · 测试（受保护）· 静态规则 · 停止门禁  │
              └────────────────────────────────────┬─────────────┘
                                                   │ 通过
              ┌────────────────────────────────────▼─────────────┐
              │  ④ 集成面 —— 并行度的真正上限                      │
              │  worktree 隔离 · 模块边界 · 任务切分 · 冲突率      │
              └──────────────────────────────────────────────────┘
```

**四个面的关系**：验证面是地基，没有它其余三个面都只是让 Agent「跑得更顺」而不是「跑得更对」；上下文面决定 Agent 读到什么；执行面决定它能碰什么；集成面决定能同时跑几个。**本方案 L1 建设 ①③，L2 建设 ②，集成面 ④ 在 P1 度量、P2 再优化。**

### 4.2 核心模块

| 模块 | 职责 | 关键设计 | 依赖 |
|---|---|---|---|
| **M1 检查入口** | 提供一条 Agent 可自主运行的 pass/fail 命令 | 每仓库暴露统一入口（如 `make agent-check`），内部聚合类型检查、lint、测试、契约校验；**退出码即结论，输出可读** | 各仓库现有工具链 |
| **M2 测试保护** | 阻止 Agent 弱化断言或删除测试 | 工具调用前置 hook 拦截对测试路径的写操作；确需修改时要求显式人工确认；CI 侧兜底比对测试数量与断言数量 | Agent 工具的 hook 能力（假设 B） |
| **M3 契约守卫** | 让跨服务改动必须走契约 | OpenAPI / protobuf 为权威源，客户端服务端代码生成物标记为只读（deny 规则 + CI 校验生成物与契约一致） | 已有契约的服务；无契约服务列入 P2 |
| **M4 停止门禁** | 把「完成」的判定权从模型手中拿走 | Stop hook 运行 M1，不通过不许结束回合；PR 侧以必需检查兜底（注意：Claude Code 在连续阻断 8 次后会强制放行，**hook 不能替代 PR 门禁**） | M1 |
| **M5 沙箱边界** | 让 Agent 在边界内免审批执行 | 文件系统与网络白名单，由操作系统对命令及子进程强制执行；替代逐条审批 | 工具沙箱能力 |
| **M6 上下文分层** | 指令按作用域加载 | 根文件（≤200 行，全局约定）→ 路径作用域规则（子系统规范）→ 就近目录文件（由 owner 维护）→ 按需 skills（流程知识）；跨工具可迁移内容写 `AGENTS.md`，工具专属机制隔离在各自目录 | 无 |
| **M7 就绪度扫描** | 度量与排序 | 每周扫描各仓库，输出就绪度评分与缺项清单 | M1–M6 的产物可被静态检出 |
| **M8 规则淘汰** | 防止上下文规则老化 | 上下文文件改动纳入 PR 评审；模型大版本发布后强制重审，删除为绕过旧模型缺陷而写的规则 | 流程约定 |

**M7 就绪度评分定义**（0–1，等权六项，各项达标记 1）：

| 项 | 达标条件 |
|---|---|
| 检查入口 | 存在统一 pass/fail 命令，且根上下文文件首屏声明了它 |
| 测试可运行 | 命令可在干净检出上跑通，无需人工前置步骤 |
| 测试保护 | 测试路径写保护 hook 已配置，CI 侧兜底校验存在 |
| 类型/静态边界 | 类型检查或等价静态检查纳入 M1 且当前为绿 |
| 上下文分层 | 根文件 ≤200 行，且至少一层作用域下沉（路径规则或子目录文件） |
| 执行边界 | 沙箱或容器化开发环境可用，且网络白名单已定义 |

> 该评分是**内部排序工具**，用于决定推广顺序与识别缺项，不用于团队考核。业界的「环境清洁度指数」（假设 A）是它的设计参考，但两者口径不同，不可互相换算。

### 4.3 关键技术决策

**决策 1：把「可验证边界」而非「规格」作为地基。**
- 备选：以规格为地基（重型 SDD）。
- 理由：约束违反与不实自述两类失配的占比随模型进步**在上升**，说明这两类问题对模型能力不敏感，只能靠硬边界解决；而规格的边际价值随模型变强而下降。
- 影响面：投入重心从「写文档」转到「改仓库」，前期见效慢，但资产不随模型换代贬值。

**决策 2：Stop hook 与 PR 必需检查双层门禁，不可只留其一。**
- 理由：Stop hook 快速反馈但可被系统在连续阻断后强制放行（Claude Code 为 8 次），存在确定的绕过路径；PR 检查不可绕过但反馈慢。两者是速度与不可绕过性的分工。
- 影响面：CI 时长成为体感瓶颈，需同步做 CI 提速（列入 P1）。

**决策 3：测试保护用「工具前置拦截 + CI 兜底」双保险，不依赖提示词。**
- 备选：在上下文文件里写「不许改测试」。
- 理由：上下文文件是建议性质，不是强制配置；而 Agent 弱化断言以求通过是已被明确记录的行为。
- 影响面：合理的测试重构会被拦截，需要一条明确的人工确认通道，否则会激起绕过行为。

**决策 4：`AGENTS.md` 承载可迁移内容，工具专属机制隔离。**
- 理由：AGENTS.md 只是「根目录一个 Markdown」的最小公约数，真正拉开差距的路径作用域、按需加载、hook、子 Agent 各家格式互不兼容；且 Claude Code 不直接读 AGENTS.md，需用 `@AGENTS.md` 导入或符号链接（Windows 下符号链接需管理员权限，统一用导入写法）。
- 影响面：一份内容一处维护，工具切换成本被控制在适配层。

**决策 5：轻量规格手法替代 SDD 工具链。**
- 形态：对较大特性，用「让 Agent 访谈我 → 产出 `SPEC.md` → 开新会话执行」。规格要求自包含：点名涉及的文件与接口、写明不在范围内的事项、以端到端验证步骤收尾。
- 理由：这实质上就是 SDD 的 specify 阶段，但没有工具链、目录规范与阶段门禁，成本低一个数量级而核心收益（验收标准前置为机器可读）基本保留。
- 影响面：规格质量依赖个人，需要沉淀一份访谈提示词模板作为团队资产。

## 5. 落地路径

| 阶段 | 目标 | 交付物 | 周期 | 验收标准 |
|---|---|---|---|---|
| **P0 验证** | 在 2 个仓库（1 个健康、1 个遗留）跑通 L1，验证假设 B 与成本估算 | M1 检查入口、M2 测试保护、M4 停止门禁；hook 能力实测报告（Claude Code / Cursor / Codex）；两仓库的真实工时记录 | 2 周 | 两仓库就绪度 ≥ 0.5；测试保护绕过次数 = 0；遗留仓库的真实工时与估算偏差记录在案 |
| **P1 试点** | 5–8 个仓库完成 L1+L2，建立度量基线，完成假设 A 复核 | M3 契约守卫、M5 沙箱边界、M6 上下文分层、M7 就绪度扫描脚本、M8 淘汰流程；轻量规格提示词模板；假设 A 原文复核结论 | 6 周 | 试点仓库就绪度 ≥ 0.6；Agent PR 首次通过门禁比例 ≥ 50%；合并冲突率完成度量；根文件 100% ≤200 行 |
| **P2 推广** | 自助化铺开，按就绪度排序 | 仓库改造 checklist、脚手架模板（新仓库默认带 M1/M2/M6）、就绪度看板 | 按季度 | 新建仓库 100% 默认就绪；存量仓库按就绪度从高到低推进，低于 0.3 的仓库先做清洁度改造再开放 Agent 自主执行 |
| **P3 可选** | 在符合切换条件的项目上试点重型 SDD | 与轻量手法的 A/B 对比结论 | 视 P1 结果 | 仅在 §3 切换条件被触发时启动 |

**排期上的两个硬约束**：
1. P1 必须完成假设 A 的原文复核，否则 P2 的「按就绪度排序推广」缺乏依据，需退化为「按团队意愿排序」。
2. 遗留仓库（无可运行测试）不进入 P1，单独立项做测试补齐，完成前**不开放 Agent 自主执行模式**（可继续使用只读问答与人工审查的编辑模式）。

## 6. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|
| 假设 A（清洁度→收益）被复核证伪 | 中 | 中——影响推广排序，不影响 L1/L2 本身 | P1 内完成复核；预设退化方案（按团队意愿排序）；L1/L2 的论证不挂靠此假设 |
| 门禁过严导致开发者绕过（关闭 hook、跳过 CI） | 中高 | 高——机制形同虚设且失去可见性 | 门禁只覆盖「已经是绿」的检查项，不引入新的失败；为测试重构提供明确的人工确认通道；监控绕过行为而非仅监控失败 |
| CI 时长成为瓶颈，双层门禁体感恶化 | 高 | 中 | M1 命令支持增量模式（只跑受影响范围）；P1 同步做 CI 提速；Stop hook 用快检查、PR 用全检查 |
| 上下文文件重新膨胀 | 高 | 中——遵从度下降，收益缓慢流失 | M8 淘汰流程 + M7 扫描的行数硬门禁；把上下文改动纳入 PR 评审 |
| 遗留仓库改造成本远超估算 | 中高 | 中 | P0 就用一个遗留仓库验证成本；超预算则该类仓库改走「只读问答 + 人工审查」形态，不强推自主执行 |
| 对抗式复核引发过度工程 | 中 | 中 | 复核提示词明确限定「只报影响正确性与既定需求的缺口」，其余按可选处理 |
| 并行 Agent 冲突率高于预期，净收益为负 | 中 | 中 | P1 先度量再决定并行度；模块边界与任务切分作为 P2 的独立议题，不在本方案内承诺 |
| 工具侧 hook 能力不足（假设 B 不成立） | 中 | 高——M2/M4 落空 | P0 实测三家工具；若某工具不支持，该工具下的仓库只保留 CI 侧兜底，并在就绪度评分中如实扣分 |

## 7. 成本估算

**人力**（单仓库，健康仓库口径）

| 模块 | 人日 |
|---|---|
| M1 检查入口（聚合现有工具链） | 1–2 |
| M2 测试保护（hook + CI 兜底） | 1 |
| M4 停止门禁 | 0.5 |
| M5 沙箱边界（白名单定义与调试） | 0.5–1 |
| **L1 小计** | **3–5** |
| M6 上下文分层（拆分、下沉、瘦身） | 2–3 |
| **L2 小计** | **2–3** |

遗留仓库（无可运行测试）需额外的测试补齐投入，量级不可一概而论，按仓库单独评估，**不计入本方案预算**。

**一次性平台投入**：M7 就绪度扫描脚本 + 脚手架模板 + 提示词模板，约 5–8 人日。

**持续成本**：M8 重审每模型大版本一轮，单仓库约 0.5 人日；CI 时长增加带来的机器成本按各仓库实际检查耗时估算。

**测算口径**：以上为**实现成本**，不含推广沟通、培训与文档。收益侧（人工审查时间下降、返工率下降）在 P1 建立基线前**不做量化承诺**——这正是 P1 要产出的数据。
